# MaaEOV 任务流程 / 工作闭环 / 日志打印逻辑审查报告

> 审查日期：2026-10-12　范围：`agent/`（8 个 .py）、`resource/base/pipeline/`（20 个 JSON，约 1050 节点）、`interface.json`、`scripts/verify_feature.py`
> 结论先行：共识别 **10 个可优化点**，按 P0（实际缺陷）/ P1（闭环健壮性）/ P2（可维护性）分级。每条附可直接复制给 DeepSeek 的结构化指令。

---

## 一、问题分析

### P0-1　mfa_agent.log 轮转机制与 FileHandler 冲突，超 5MB 后直写日志全部丢失
- `agent/mfalog.py` 中 `_emit()` 的轮转用 `os.replace(_LOG_PATH, _LOG_PATH + ".1")`；
- 而 `configure_stdlib_logging()` 又在**同一文件路径**上挂了一个常驻 `logging.FileHandler`；
- Windows 下对已打开句柄的文件执行 `os.replace` 会抛 `PermissionError`，被 `except: pass` 静默吞掉——**且 `os.replace` 位于 `open(...)/write` 之前，异常会连带跳过本次写入**。即：文件一旦超过 5MB，所有 `mfa_log` 直写明细从此不再落盘，只剩 stdlib 行，`mfa_agent.log` 失去"唯一可靠明细载体"的作用。

### P0-2　自动推图进度计数器跨任务运行不复位
- `agent/auto_battle.py` 的模块级 `_PROGRESS = {"current": 0, "done": 0}` 注释称"每次加载项目归零"，但代码中**没有任何复位点**；agent 子进程随 GUI 常驻，同一会话内第二次运行"自动推图"时关卡计数会从上次的值继续累加，进度播报失真。

### P1-1　SoCGBPickAvailable 遮蔽 SoCGBSwipe，失败路径直接击穿任务闭环
- `认知海域.json`：`SoCGBLoop.next = ["SoCGBPickAvailable", "SoCGBSwipe"]`，两者均为 DirectHit → `next` 首匹配胜出，`SoCGBSwipe` **永远不会被扫到**；
- 更关键的是 `SoCGBPickAvailable.run()` 返回 `clicked > 0`：当一张卡都没点成（选满/异常/超 wall_cap）时返回 `False`，MaaFw 视为节点动作失败 → 整个任务误报失败，而不是走滑动兜底。与项目既定的"条件不满足则优雅退出"范式（`override_next` 自然结束）相悖。

### P1-2　15 个入口任务完全没有 focus，GUI 运行日志对它们是黑盒
- 全管线约 1050 节点中仅 `认知海域.json`(33)、`PastEvent.json`(18)、`CrisisMissionTickets.json`(8)、`CurrentEvent.json`(2)、`Shared.json`(3) 配置了 focus；
- 启动游戏、清体力、事务所、补给站、外部招募、联线封锁、市区巡逻、领取邮件/奖励/协议、阈限禁区、推图、退出游戏等任务**无任何 focus**，GUI 右侧运行日志看不到步骤进度；
- 其中"自动推图"的进度只靠 `播报进度` CustomAction 走 agent 通道（stdout 被 GUI 丢弃 + 只写 mfa_agent.log），**用户在 GUI 里完全看不到第 N 关**——与认知海域的高质量进度展示形成断崖。

### P1-3　日志无会话边界，跨次运行难以切分归因
- `mfa_agent.log` 与 stdlib 落盘均为追加写，没有任务开始/结束的会话分隔符；排查"昨晚那一次失败"时只能靠时间戳猜测任务边界。

### P1-4　soc_trace.py 只服务认知海域，诊断工具未泛化
- 节点→中文步骤的映射表 `STEP` 是硬编码的 SoC 专表；其他任务失败仍需手工按 `task start:` / `Node.PipelineNode.Starting` 顺序翻 maafw.log。而各节点 focus 文本本身就是现成的步骤字典，未被复用。

### P1-5　「放弃未完成的联线封锁挑战」No 分支用 StopTask，与优雅退出范式不一致
- `interface.json` 中该 option 的 No case 为 `"action": "StopTask"`。按 Maadori v1.1.0 的迭代教训，强停类收尾在"半完成状态 + 主界面空转"场景下体验差；至少应在 doc 中明确其行为语义，或改判定节点本身优雅退出。

### P2-1　危机行动与往期活动约 90% 代码重复
- `crisis_mission.py` 与 `past_event.py` 的 `_parse_ticket`、`_ZERO_LOOKALIKES`、滑块/加号坐标常量、`_click`、设置战斗次数的整套流程几乎逐行相同（phase 命名不同）。修一处漏一处的典型温床（本次审查即发现两者 OCR 归一化逻辑已是两份拷贝）。

### P2-2　interface.json「选择往期活动」override 样板大量重复
- 7 个活动 × 4 个重试节点 + 3 个链路 override ≈ 300 行纯复制粘贴；新增一个往期活动要手改 7 处，极易漏改（`选择往期活动_重试4` 就是靠复制堆出来的）。

### P2-3　示例残留文件 my_action.py / my_reco.py 仍在 agent 目录
- `main.py` 已注释掉对它们的导入；`my_reco.py` 里还留着会改动全任务管线的 `override_next` 演示代码，一旦被误 import 有实际风险；同时它们干扰 `verify_feature.py` 的 custom_action 注册清单核对。

### P2-4　verify_feature.py 校验面可再扩展
- 现有 8 类检查已覆盖扫荡链 timeout，但缺：① 全管线"长等待节点未显式写 timeout"的 lint（本次实测仍有约 240+ 带 next 的节点未显式设 timeout，多数是纯导航节点问题不大，但战斗/结算类漏网的查不出来）；② focus 覆盖率报告；③ v5 禁用字段（`interrupt`）扫描防回归。

### 优化点 1（P0）重构 mfalog.py 落盘通道，修复轮转失效

**修改范围**：仅 `agent/mfalog.py`。
**实现要求**：
1. 删除 `_emit()` 内的手工 `os.replace` 轮转与手写 `open(..., "a")`，统一改用 `logging.handlers.RotatingFileHandler(_LOG_PATH, maxBytes=5*1024*1024, backupCount=3, encoding="utf-8")` 作为唯一落盘通道；
2. `mfa_log/_emit` 的直写改为经由一个专用 logger（如 `_disk_logger`，propagate=False，仅挂该 RotatingFileHandler），`configure_stdlib_logging` 的 root FileHandler 也替换为同一个 RotatingFileHandler 实例（共享，避免双句柄）；
3. 保留 stdout 的 `[MFA]{json}` 单行输出与 flush 行为不变；保留 redact 全部逻辑不变；
4. 兼容旧文件：启动时若发现旧 `_LOG_PATH` 超过 maxBytes，做一次性归档（改名 `.old`）后重建。
**预期效果**：`mfa_agent.log` 超过 5MB 时正常轮转出 `.1/.2/.3`，任何时刻直写明细不丢失；Windows 下无 PermissionError。
**验收**：手工把 maxBytes 临时调成 10KB 跑一次认知海域，确认 `.1` 出现且无写入丢失；`verify_feature.py` ALL_OK。

**指导语句（复制给 DeepSeek）**：

> 请重构 MaaEOV 项目的 agent/mfalog.py（仅此一个文件），修复日志轮转缺陷。现状：_emit() 用手工 os.replace 轮转 debug/mfa_agent.log，但 configure_stdlib_logging() 又在同一文件挂了常驻 logging.FileHandler，Windows 下句柄占用导致 os.replace 抛 PermissionError 被静默吞掉，且异常会跳过本次写入，文件超 5MB 后 mfa_log 直写明细全部丢失。要求：1) 用 logging.handlers.RotatingFileHandler(maxBytes=5MB, backupCount=3, encoding="utf-8") 作为唯一落盘通道，mfa_log 直写与 stdlib 接管共用同一个 handler 实例（专用 logger propagate=False）；2) 保持现有 [MFA]{json} 单行格式、stdout flush 行为、redact 打码逻辑、mfa_log/mfa_err/mfa_warn 签名完全不变；3) 启动时对超限旧文件做一次 .old 归档；4) 改完在文件头注释中说明轮转机制。不得改动其他文件。完成后运行 python scripts/verify_feature.py 必须输出 RESULT: ALL_OK。

### 优化点 3（P1）修复 SoCGBPickAvailable 失败击穿与 SoCGBSwipe 遮蔽

**修改范围**：`resource/base/pipeline/认知海域.json`（SoCGBLoop / SoCGBPickAvailable / SoCGBSwipe / SoCGBContinue 一带）与 `agent/soc_actions.py`（SoCGBPickAvailable 返回值语义）。
**实现要求**：
1. `SoCGBPickAvailable.run()` 改为**恒返回 True**，"点没点成卡"的信息通过 mfa_log 输出（附 clicked 数）；将"是否还有卡可选"的判定下沉到管线：新增/改用模板门控节点（OCR「未激发」或已有 `SoCState_GB1/GB0` 判据）决定 `SoCGBLoop.next` 走选卡还是滑动还是继续；
2. `SoCGBSwipe` 不得再被 DirectHit 兄弟节点遮蔽：把"是否需要滑"改为由识别门控（如右缘存在半张未激发卡）触发，或保持 DirectHit 但置于 PickAvailable **之前**仅当其内部明确发出需要滑动的信号时可达——具体取哪种以不引入 `interrupt`（v5 禁用）为前提，自行评估后择一并在节点注释中说明理由；
3. 所有改动节点显式写 `timeout`；选卡→继续的全链路覆盖 SoCAwaitBattle 的 max_wait（≥600s 的前序预算规则照旧）；
4. 每个被改节点保留/补齐 focus 中文提示。
**预期效果**：选满 5 卡后自然收敛到点「继续」；无卡可点时不再误报任务失败；滑动兜底真实可达。
**验收**：`verify_feature.py` ALL_OK + 实跑一次认知海域，GUI 日志能看到"全局 Buff 选卡 → 收敛 → 继续"的完整步骤且无 fail。

**指导语句（复制给 DeepSeek）**：
