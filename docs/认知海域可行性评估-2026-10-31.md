## 0. 结论

1. **认知海域至今没有实机跑通过一次。** `debug/maafw.log` 全量检索 `#SeaOfCognition` 无 `Tasker.Task.Starting` 记录，`debug/mfa_agent.log` 无任何 `gb_pick` / `await_battle` 事件 —— 两个 CustomAction 从未被真正执行。此前"完成 70–80%、12 步闭环"的判断只有代码层面的依据，没有运行层面的依据。
2. **找到一个必然导致功能失效的结构性 bug**：`SoCGBPickAvailable` 的 `custom_action` 写在 `action` 顶层而非 `action.param` 内，框架反序列化后拿不到动作名，**该节点形同 DoNothing**。全库 15 处 Custom action 中只有它一处写错。已修。
3. **修完这一条，"能不能跑"才有意义。** 在此之前谈 Buff 优先级、节点评分、路线规划都是空谈 —— 选卡动作根本没运行。
4. **玩法收益天花板低是事实，但不影响做不做**：每周 2 次、每次省 10–15 分钟。合理目标就是"每周自动跑完两次、失败会停下并留证"，**不是**复刻 MAA 肉鸽。
5. **工作量修正**：`P0 稳定化` 从原估 2–3 人日上修到 **4–6 人日**，主因是实机验证从未做过，ROI 与 OCR 判据都要靠实跑回填。

## 2. 当前真实拦路问题（按严重度）

### P0-1 选卡动作从未执行（已修）

```jsonc
// 修复前 —— 错
"action": { "type": "Custom", "custom_action": "SoCGBPickAvailable" }

// 修复后 —— 与全库其余 14 处一致
"action": { "type": "Custom", "param": { "custom_action": "SoCGBPickAvailable" } }
```

依据：`maa/pipeline.py` 中 `JAction{type, param}`，`JCustomAction{custom_action, ...}` 属于 **param** 的变体。写在顶层时 param 为空，动作名丢失。

后果链（未被日志证实但机理确定）：`SoCGBPickAvailable` 变成空动作 → 立即 `next` 到 `SoCGBContinue` → 一张 Buff 都没选就点「继续」→ 游戏弹「未选择灵感／是否放弃激发」→ `_SoCGBAbandonConfirm` 点 ✓ 放弃 → 回 `SoCGBLoop` → 循环。**结果不是崩溃，而是"看着在跑，全局 Buff 永远是 0 张"** —— 这种失效比报错更难发现。

同一处还修了两个衍生问题：
- `SoCGBLoop.next` 原为 `[SoCGBPickAvailable, SoCGBSwipe]`。前者是 `DirectHit`（必中），第二项**永不可达**，已移除（滑屏由 CustomAction 内部负责）。
- 原注释称"PickAvailable 返回 False → 框架试下一项"。**错**：next 按识别命中顺序推进，不看 action 返回值；返回 False 只会判节点失败并走 `on_error`。已补 `on_error: ["SoCGBContinue"]`，让"一张没选到"也能落到兜底而不是整个任务失败。

### P0-2 队列顺序：先关游戏再跑海域（已修，但属本机配置）

`config/instances/default.json` 的 `CurrentTasks` 中 `#ShutDown` 原本排在 `#SeaOfCognition` 之前。已把认知海域移到 `#一键领取` 之后、`#ShutDown` 之前。

同时清掉一条脏数据：原列表末尾还有 `"认知海域<|||>#SeaOfCognition"`，而 `interface.json` 里根本没有名为「认知海域」的任务项（只有「认知海域（开发中）」），重复且无效。

> ⚠️ `config/instances/*.json` 被 `.gitignore` 忽略（第 66 行），是**本机实例配置**：
> ① 不入库、不随发版下发；② GUI 保存配置时会重写该文件，改动可能被覆盖。
> 因此这条修复只解决"本机现在能跑"，**根因仍需在 GUI 里把认知海域拖到退出游戏之前并保存**。若想避免反复被覆盖，建议新建一个专用实例配置。

**另一个连带问题（未改，待确认）**：`CurrentTasks` 里 `#ShutDown` 之后还挂着 7 条。核对 `interface.json` 的 `task[]`（共 16 项）：

- **6 条指向已不存在的任务项**：`#Mailbox`、`#ShortTermCheckIn`、`#DailyStaminaBonus`、`#CountermeasureProtocol`、`#CollectRewards`、`#ExitApp` —— 这些任务项在 `interface.json` 里已并入「活动领取」「一键领取」后删除，但实例队列没同步。
- **1 条任务项存在但顺序失效**：`#自动推图` —— 排在关游戏之后，永远不会执行。

属于任务合并后的遗留脏数据。清不清需要你确认（也可能是有意保留的备用队列），本次未动。

### P0-3 层级选项缺繁简兼容（已修）

基础节点用 `[梦夢][渊淵][层層]`，但 `interface.json` 的「深潜层」「朦胧层」两个 case 直接写死简体。已统一为 `[深][潜潛][层層]` / `[朦][胧朧][层層]`。

### P0-4 注释与实现漂移（已修）

| 位置 | 注释声称 | 实际 |
|---|---|---|
| 全局 Buff 段 | "5 张卡面模板已就位：能量涌流/战前准备/环境遮蔽/应急护盾/身心调和" | **这 5 张图根本不存在**，目录下只有 10 张，全部已被引用 |
| `SoCGBLoop` | "返回 False → 框架试下一项 SoCGBSwipe" | 机制错误，见 P0-1 |
| `SoCInspirationFallback` | "必须排在 SoCResume.next 的最后" | 它**不在** `SoCResume.next` 里，只在 `SoCContinueDive.next` |

### P0-5 校验脚本漏检（已修）

`scripts/verify_feature.py` 第 7 段只读 `action.param.custom_action`，写错位置的节点会被**静默跳过**，于是 `RESULT: ALL_OK` 掩盖了 P0-1。已新增一条硬性检查：`type == "Custom"` 但 `custom_action` 出现在 `action` 顶层 → `[FAIL]`。修复后该段 action 清单里 `SoCGBPickAvailable` 才出现。

### P1-1 三处全屏 OCR + Click 有误点风险（未修，需实图）

| 节点 | expected | 风险 |
|---|---|---|
| `SoCSelectLayer` | `[梦夢][渊淵][层層]`，roi 全屏 | 「梦渊层」在节点按钮、右侧详情标题、说明文字里都可能出现；OCR 点的是首个命中框，可能点在只读文字上 → 空点 |
| `SoCClaim` | `[领取]/[确认]`，roi 全屏 | 「确认」几乎任何弹窗都有，**最容易误点**；且它挂在 `SoCResume.next` 第 1 位 |
| `SoCDeepDiveFree` | `["自由探索","自由","探索"]` | 单词级 expected 过宽，任意含「探索」的文案都会命中 |

这三处不是"改个 roi 就行"，必须拿实机截图定边界，否则是把一种错换成另一种错。

### P1-2 券尽判定覆盖不全

`_SoCNoTicket` 只挂在 `SoCSelectLayer` 与 `SoCTeamEnter` 的 next 里。在中途（如局内 Buff 屏）券尽/异常，无法收敛到 `SoCDone`，只能靠超时。

### P1-3 `SoCResume` 的探测项本身带点击

13 个探测项全部是"识别 + 动作"，命中即执行。这是"任意界面续跑"的实现方式，但也意味着**探测项的识别精度 = 误点风险**。结合 P1-1，`SoCClaim` 排第 1 位是全链最危险的一环。

### P2 结构性短板

- 单文件 895 行，注释约占一半，历史决策层层堆叠，无法判断哪段是现行逻辑。
- 无 `SoCStatus` 局内状态（层数、剩余灵感、券数、积分），"记住选过哪张卡"只能塞进 Python。
- 无离线回归，改一次 pipeline 要重载资源跑一遍，反馈环 1–3 分钟。

## 5. 可行性分档（修正版）

| 目标 | 判断 | 主要工作 | 工作量 |
|---|---|---|---|
| **A. 每周自动跑完两次、失败会停** | **可行（技术风险低，验证成本高）** | 实机跑通 1 次完整流程 → 按实图回填 3 处 OCR 的 roi → 补券尽收敛 → 删/改盲点 | **4–6 人日** |
| **B. 可配置日常任务（层级/队伍/Buff 偏好）** | 可行 | 拆目录 + `resource/base/data/soc/*.json` + 选卡接优先级表 | **+3–5 人日** |
| **C. MAA 肉鸽级完整模块（地图感知+路线规划+构筑）** | **不建议** | 地图识别 + 节点评分 + 局内状态 | 20–30 人日，奖励不增 |
| **D. 复刻 BlackFlow 的 ONNX 连线感知** | **不做** | 需 onnxruntime（agent 侧无）+ 标注流水线 | 15+ 人日，场景不匹配 |

判断依据不是"技术难不难"，而是：

- **战斗被游戏代劳**：进战即自动，MAA 最重的 42KB 战斗插件在这里等价于"点一次开始作战"。
- **周限次**：每 14 天 7 张券，跑满 1000 分只要 2 次。自动化的边际收益到此为止。
- **失败成本低**：单局 10–15 分钟，重跑即可，不需要精细恢复。
- **真正的复杂度在 UI 时序**（结算空白页 → 弹窗 → ✓ → 继续），这部分已经用 `SoCAwaitBattle` 的轮询解决了，是当前写得最扎实的一块。

## 6. 建议路线

### 第 1 步 · 先证明"能跑"（1–2 人日，必做）

单跑 `#SeaOfCognition`，梦渊层，盯全程。检查点：

1. `debug/maafw.log` 出现 `Tasker.Task.Starting [entry=#SeaOfCognition]`
2. `debug/mfa_agent.log` 出现 `SoC gb_pick START` —— 这条出现，才算 P0-1 真的修好了
3. `gb_pick END 已点=N`，N ≥ 1
4. 全局 Buff 界面截图核对：是否真的选满了

> 如果第 2 条没出现、而节点又"过去了"，说明还有别的地方把 action 吞掉了，回头查 `PipelineParser` 的 parse 日志。

### 第 2 步 · 修 OCR 污染（1–2 人日）

拿第 1 步产生的截图，为 `SoCSelectLayer` / `SoCClaim` / `SoCDeepDiveFree` 各定一个紧 roi。原则：

- **能点的地方才给 roi**，别用全屏。
- `SoCClaim` 的「确认」要么缩到弹窗区域，要么换成只认「领取」+「获得」。
- 单词级 expected（`"自由"`、`"探索"`）全部删掉，只留完整短语。

### 第 3 步 · 补券尽与失败收敛（0.5–1 人日）

`_SoCNoTicket` 补挂到局内 Buff / 继续下潜两条链的 next 尾部；`SoCBattle` 失败时明确 `_StopTask` 而不是继续点。

### 第 4 步 · 配置化（3–5 人日，可选）

只有第 1–3 步稳定跑满两周再做。首选落点是**选卡策略**（现在是"见卡就点"），把 `SoCGBPickAvailable` 里 OCR 到的卡名对照 `buff_priority.json` 排序。注意：**必须用 OCR 读卡名，不能靠卡面模板** —— 卡面匹配实测 0.18–0.53，不可用。

### 不要做

- 不要引入 ONNX / cv2 到 agent（运行时不带这些库）。
- 不要为"路线规划"上 CNN。认知海域奖励主要由"打没打"决定，不是"走了哪条路"。
- 不要在没跑通之前重构目录。895 行确实该拆，但拆完还没跑通等于把问题藏得更深。
