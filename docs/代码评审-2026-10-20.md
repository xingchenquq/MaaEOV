**工程质量在该规模 MaaFramework 项目中属上乘**，三点值得肯定：

1. `verify_feature.py` 的 11 段校验（死链、跨文件同名、override 引用、扫荡链 timeout、ROI 越界）已成 CI 强制门禁，且 `gen_flow_doc.py` 保证流程文档与 pipeline 同步——这类"结构性防回归"在同类项目里很少见。

## 三、分维度详评

### 3.1 架构与模块划分

**分层是清晰的**：pipeline（流程编排）→ `interface.json`（任务/选项/override 装配）→ `agent`（需要判断力的动作）。

**问题一：`auto_battle.py` 职责混杂。** 它同时承担"公共库"（`_parse_param` L30、`_screencap` L166、`_save_png` L128）与"业务动作"（`ReportProgress` L50、`ClickTopToExit` L91、`SaveFailShot` L184）。后果是 `soc_actions.py` L44 直接 `from auto_battle import _parse_param, _screencap`——**跨模块引用下划线私有函数**，且方向倒置（认知海域模块依赖自动推图模块）。目前不构成循环导入，但任何一方重命名都会连锁失效，且"自动推图"这个业务名承载了全局基础设施，语义误导。

**问题二：`Shared.json` 仍是巨石。** 248 节点 / 5 363 行 / 131 KB，内含 166 个 `_内部`、70 个 `~汇点`、12 个公共动作。前次拆分（20 文件）已解决 90% 问题，但剩余这一个是所有任务的最强耦合点：修改任一公共节点，全部 19 个任务的回归面同时打开。

**建议的目标结构**（成本低、可渐进）：

```
agent/
  common/            # 新增，纯工具，无业务
    params.py        # _parse_param
    screen.py        # _screencap / save_png（含非 ASCII 路径加固）
    click.py         # click + 重试 + 结果返回
    log.py           # 现 mfalog.py 迁入
  actions/           # 每模块只留业务动作
    battle.py  sweep.py  soc.py  report.py
```

### 3.3 错误处理与健壮性（本次评审的实质缺陷集中区）

**① 点击失败被静默吞掉，无重试、无传播。**
5 处 `_click` 全部是"捕获异常 → 记一条 error → 返回 None"。调用方无法得知失败，于是继续走流程 → 下游识别全 miss → 节点超时 → 最终报 `Task timeout`。用户日志里只看到"任务失败"，真正根因（一次点击丢失）被埋掉。这类"错误在最内层被吞、在最外层才炸"的模式，是排障成本最高的反模式。

**② 超时后"假成功"。**
`soc_actions.py` L136-137：`SoCAwaitBattle` 等满 `max_wait=540s` 仍未见到"继续"按钮时，只打一条 warn 就 `return True`。pipeline 认为战斗结算完成，继续下一轮 → 下一轮继续卡。正确做法是返回 `False` 让任务明确失败，或至少 `mfa_err`（当前是 warn，用户在 GUI 里不会注意到）。

**③ 同一解析函数，两处边界策略不一致（真实缺陷）。**
`past_event._parse_ticket` 的结果被 `max(0, min(6, n))` 约束（L82）；`crisis_mission` 只有 `max(0, n)`（L61），**无上限**。而 OCR 把"5"读成"50"并非极端情况（`_ZERO_LOOKALIKES` 本身就承认 OCR 不可靠）。
后果链：`_TICKET_COUNT=50` → `SetCrisisMissionSweepCount` 点 49 次加号（每次 0.8s ≈ 39s）→ 次数溢出界面或点空 → 实际问题被伪装成"扫荡失败"。上限值只需与游戏内调令上限对齐即可，成本一次改动。

**④ 停止响应延迟。**
`SoCAwaitBattle` 的 `time.sleep(init_wait)` 默认 30s 不检查 `context.tasker.stopping`，轮询内的 `sleep(poll)` 同理。用户点"停止"后最长 ~35s 无反应。分段 sleep 即可解决。

**⑤ 诊断截图写盘不可靠 + 无限增长。**
`soc_actions._save_gb_diag`（L313）用 `cv2.imwrite`，**不检查返回值**。项目自己的记忆明确记录过"cv2 不支持非 ASCII 路径"——若用户装在 `D:\游戏\MaaEOV`，`imwrite` 静默返回 False，函数继续打印"截图已保存"，排障时拿到的是不存在的路径。同时该函数在每次 SoC 任务的首轮**无条件**落盘，无保留上限，`debug/gb_diag/` 会长期膨胀。
建议改为 `cv2.imencode(...)[1].tofile(path)`（或统一走 `common/screen.save_png` 的 numpy+zlib 实现），并加"仅失败时保存 + 保留最近 N 张"。

**⑥ 日志落盘路径推导不一致。**
`mfalog.py` L81 用相对路径 `"debug/mfa_agent.log"`（依赖 CWD）；`auto_battle.py` L27 用 `Path(__file__).parent.parent/"debug"`。CWD 不是程序根时（例如从 IDE、或从其他目录 `python agent/main.py`），日志会落到两个不同位置。且当前仓库里 `debug/mfa_agent.log` 为 0 字节，说明这条"唯一可靠的明细载体"尚未被验证过真的写进去了——**建议加一次冒烟验证**。

**⑦ `except Exception` 范围偏宽但多数可接受。** `main.py` L24 的导入兜底（写 stderr + raise）是正确的；`_parse_param` 的双重 JSON 兜底也合理。唯一值得收紧的是 `_screencap`（L166）：截图失败返回 None，调用方普遍只 `continue`，无"连续失败 N 次则中止"的判据，理论上可无限循环到 `max_wait`。

### 3.4 性能

**① 固定等待是最大开销项。**
`post_wait_freezes: 1000` 出现 122 次、`post_delay` 61 次（多为 1000ms）。按一次完整日常约 250–350 次点击估算，纯等待约 4–6 分钟。这是稳定性的必要成本，但**未做过分级**：导航类点击（进菜单、切页签）与战斗结算类点击用了同一个 1000ms。
建议按类别分级（导航 500ms / `threshold` 0.85，战斗结算保持 1000–1200ms），需实机 A/B 验证后再压缩。

**② `next` 长列表的排序未按命中率优化。**
`_NavigateHomepage` 27 项、`_Escape*` 21 项 × 10。Maa 按顺序逐项试探，每次试探 = 一次完整识别（模板匹配或 OCR）。列表顺序目前是按"逻辑归类"排的，不是按"实际命中频率"排的。
这是**零风险纯收益**优化：从 `mfa_agent.log` 抽 `Node.PipelineNode.Succeeded` 序列，统计各 next 列表的命中分布，把高频项前置。导航类节点响应时间预期降 30–50%（取决于当前排序与实际分布的偏差）。

**③ SoC 轮询的资源浪费。**
`SoCAwaitBattle` 每 5s 截图 1 次 + 点击 2 次；战斗通常 60–120s，其中约 80% 的轮次注定检测不到任何目标。把 `poll` 拉到 8–10s、或前 60s 只做轻量截图比对（帧差）可降低模拟器与 OCR 压力。收益是体感层面的（降低模拟器卡顿概率），不是耗时。

**④ `mfalog._emit` 每行 `stat` + `open/close`。**
高频日志下 IO 放大。当前日志频率低（每 5s 一条量级），**暂不构成问题**，仅在日志量上来后需要改为持有文件句柄。

### 3.5 可读性与一致性

**① `action` 两种写法混用。** ~150 处 `"action": "Click"` 字符串简写，与显式 `{"type":"Click","param":{"target":[x,y,1,1]}}` 并存。而项目自定约定是"**Click 必须带显式 target，否则行为未定义**"（`开发记录.md` L192）。简写实际依赖 Maa 的隐式回退（点识别框中心），当识别结果是**多行 OCR** 时，点哪个框由框架决定。
存量 608 节点已在跑，不建议回改；但**新节点应一律显式**，并把约定改为"导航/固定 UI 用显式 target，依赖识别位置的动作才用简写"，避免约定与现实互相打脸。

**② 命名中英混用**（97 中文 / 511 英文）。中文名集中在公共节点与 `PastEvent`/`推图`。改名风险高（override 引用面广），不建议批量重构；建议新节点统一英文，中文只走 `focus` 文案。

**③ 同一 ROI 重复 48 次**（`[821,70,240,115]`，共时性/公平交易标题区）。JSON 无常量机制，但可在 `Shared.json` 顶部注释登记"高频 ROI 清单"，降低改 UI 时的漏改概率。

**④ 注释质量高但存在过期风险。** `认知海域.json`、`推图.json` 的注释精确到"裁自实机失败件 [x,y,w,h]"，这是很好的实践；但 `verify_feature.py` 无法校验注释与代码的一致性，UI 改版后注释会悄悄过期。

### 3.6 工程化与校验

现有 CI（`verify.yml`）只跑标准库脚本，这个取舍很聪明。缺口在于：

**① 注册核对存在假阳性。** `verify_feature.py` L120-129 扫描**全部** `agent/*.py` 收集 `custom_action`/`custom_recognition` 名，但运行时只加载 `main.py` 实际 `import` 的模块。`my_action.py`（`my_action_111`）与 `my_reco.py`（`my_reco_222`）在 `main.py` L17-18 被注释掉、从未加载，却仍被计入"已注册"清单。若将来 pipeline 引用这两个名字，校验会通过、运行时必然失败。

**② 模板存在性只扫 pipeline，不扫 override。**
第 6 段（L221-236）只检查 pipeline 节点的 `recognition.param.template`。而 22 张"静态扫不到引用"的图片恰好全部通过 `interface.json` 的 `pipeline_override` 接入（`危险地带_CS111/CS112`、`战斗编队2/3`、6 个往期活动封面）。这意味着：**override 里把模板名写错，校验照样 ALL_OK，运行时才开始报识别失败**。这是当前校验体系里最大的一处盲区。

**③ timeout 检查靠节点名关键词，覆盖面窄。**
第 9 段用 `sweep_keyword()` 猜（`_Sweep*` / 含"战斗次数" / `点击出发` / 含"快速完成" / 含"等待…结果"）。564 个节点无显式 timeout，其中 316 个是非终端节点。已记录过的"`_SweepMax` 缺省 20s 炸弹"就是靠人工发现、而非校验捕获的。命名一变，校验就失效。

**④ 缺依赖声明与单元测试。**
无 `requirements.txt` / `pyproject.toml`，`/python/` 被 gitignore → 新克隆无法重建开发环境。`_parse_ticket`、`_parse_param`、`_redact`、`strip_jsonc` 四个纯函数边界多（OCR 变体、双重 JSON 编码、凭证正则、注释剥离），最适合用 pytest 锁住，目前 0 覆盖。

**⑤ 打包脚本小缺口。**
`package_full.py` L23 的 `SKIP_DIRS` 未含 `.github`、`.mimosa`（会被打进发布包）；打包后无内容复核（`build_resource_zip.py` 有 `LEAK_MARKERS` 复核，两者不对称）。

## 五、不建议改动（避免过度设计）

这几点看起来像问题，但改动收益低于风险，建议维持现状：

1. **把 608 个节点全部补上显式 `timeout`** — 逐节点实测需要完整回归，而现有 44 个 + 关键词校验已覆盖已知高危链。应按任务链逐个补，不要一次铺开。
2. **把 97 个中文节点名改成英文** — override 与 `focus` 引用面太广，收益是"看起来整齐"，风险是引入死链。
3. **合并 `_Escape1~9`** — Maa 的节点无参数化机制，链式逃生本质上需要 N 个不同 `next` 的节点。用 CI 一致性校验（建议 11）约束，比强行合并更实际。
4. **给 608 个节点补 `on_error`** — 会掩盖真实失败。`on_error` 应只用于"已知可恢复"的场景（当前 1 处用得是对的）。
5. **给 OCR 全量加 `expected` 变体容错** — 会降低识别精度并放大误匹配。已在 `_ZERO_LOOKALIKES` 与 `SoCGBPickAvailable` 的 `label` 列表做了必要的最小容错，够了。
