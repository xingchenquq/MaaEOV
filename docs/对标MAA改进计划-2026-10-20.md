## 0.5 三方对照与二次校准（追加于 2026-10-20，参照 Maadori v1.6.5）

本计划初稿只拿 MAA 一个参照物，但 MAA 是**零 agent 的纯 pipeline 项目**，而本项目与隔壁 Maadori 都是 **MFAAvalonia + Python agent**。补看 Maadori 后，有 4 处结论必须修正。

### 三方定位

| 维度 | MAA v6.19.0 | Maadori v1.6.5 | MaaEOV v1.14.7 |
|---|---|---|---|
| 逻辑载体 | 3970 节点全 pipeline | `src/maadori/` **8324 行 Python** + 369 节点 pipeline | 608 节点 + agent **1126 行** |
| agent 定位 | 无 | 主体（pipeline 只做界面导航） | 辅助（战斗/Buff/货币解析） |
| 测试 | 无 | **pytest 30+ 文件** + ruff + CI | **0 个测试**，无 pytest/ruff 配置 |
| 静态护栏 | 无（靠人工） | `debug/check_closure.py` 73 行，接 CI，退出码 0/1/2 | `verify_feature.py` 397 行，11 段，退出码 0/1 |
| 发版校验 | `filelist.txt` + `changes.json` | `debug/frozen_check.py` 解 PyInstaller 包验符号 | 无（仅打包脚本） |
| 打包形态 | NetBeauty 扁平化 | PyInstaller 单 exe | 解释执行（`python/` + `agent/`） |

**结论**：**pipeline 侧的课要跟 MAA 学，agent 侧的课要跟 Maadori 学。** 初稿把两者混在一起，导致 P0 全压在 pipeline 上，忽略了 agent 侧"零测试"这个更大的结构性问题。

### 四处校准（均为实测，非推测）

**校准 1｜316 → 221：P0-2 的量被高估了 30%。**
初稿把"无 `timeout` 的非终端节点"一律算作风险。但按 MaaFramework 语义，若某节点的 `next` 里存在**即时命中候选**（`recognition` 缺省或 `DirectHit`），扫描会在第一个候选立刻返回，不吃 20s 预算。实测分类：

| 分类 | 数量 | 处置 |
|---|---|---|
| 非终端节点总数 | 356 | — |
| 无 `timeout` 总 | 316 | — |
| ├ A：`next` 中含即时命中候选 | **95** | **不补**（补了反而是噪音） |
| └ B：全部候选都需等待（真风险） | **221** | 必须补，按文件分批 |

B 的分布：`Shared.json` 60、`推图.json` 29、`认知海域.json` 25、`PastEvent.json` 23、`TheRoom.json` 23、`Supplies.json` 15。

**校准 2｜陷阱自环实测为 0，该项从"存量修补"降级为"回归护栏"。**
Maadori 的实测教训：26 个"自环 + 无 on_error/timeout"节点，按严格判据（`next` 去掉自身与 `[JumpBack]` 后无剩余候选）筛，**真陷阱 0 个**——`[X, self]` 是"重试 + 备选"的正常写法。本仓库实测更干净：

| 指标 | 实测 |
|---|---|
| 自环节点 | 1 |
| 有 `on_error` 的节点 | 1 |
| 严格判据下的陷阱 | **0** |

因此图论检查的价值不在"修存量"，而在"防下一次改动引入"——仍要做，但工作量从 0.5 人日降到 0.2，且定位为护栏（见新增 P0-4）。

**校准 3｜agent 侧缺的是"可测试性"，不是"更多动作"。**
- 本仓库 agent 1126 行、8 个平铺文件、**0 个测试**、无 pytest/ruff 配置。
- 已知的 `_parse_ticket` 无上限缺陷（OCR 把 5 读成 50 → 49 次加号点击），**一个 3 行单测就能拦住**。
- 依赖方向反了：`agent/soc_actions.py:44` 从 `agent/auto_battle.py` 导入私有函数 `_parse_param` / `_screencap`——通用工具被放在业务模块里，业务模块之间横向耦合（Maadori 用 `base.py` 明确规定 `base ← recognitions/actions ← core`，禁止反向引用）。
- `crisis_mission.py` 与 `past_event.py` 59.2% 相似（56 行逐字相同），属重复而非分工。

→ 新增 P0-5（纯函数单测）与 P1-7（agent 包结构）。

**校准 4｜P1-6 的结论被 Maadori 独立印证，维持"不做字段"。**
Maadori 对同一问题的判断：MaaFramework 对未知字段是容忍、警告还是报错**尚未验证**，故其 `pipeline 自文档` 列为 P2 且需前置实验。本项目 pipeline 是 JSONC，`//` 注释已达同等效果——**不引入 `Doc` 字段**，只补注释规范。

### 同时被 Maadori 反向确认的两条风险

1. **同名节点覆盖行为未验证**：Maadori 指出 MaaFramework 可能继承 MaaCore"不允许重名"的约束，"轻则覆盖不生效，重则资源加载直接失败"。本计划 P2-7（覆盖层）继续压后，且前置实验写进该章。
2. **MFA 增量包范围 = `interface.json + resource/ + agent/`，不含 `data/`**（Maadori 在 `config.py` 注释中已踩过）：这直接决定 P1-5 的纠错表**必须**落在 `resource/` 下，不能放 `data/` 或 `config/`，否则老用户拿不到。

## 2. P0-1：OTA 安全化（白名单清理 + 启动自检）

### 2.1 目标
消除"资源 OTA 更新后 `agent/` 被清空或旧文件残留导致资源加载失败"的致命风险，使更新失败可被用户与开发者同时看见。

### 2.2 现状依据
- 项目记忆已记录：*Maadori v1.4.4 实测 MFA 全量更新分支会无条件删除 `resource/` 与 `agent/` 下的旧文件，再按包内容复制；若资源包不含 `agent/`，用户侧 `agent/` 被清空 → 程序失效*。MaaEOV 是否走同一分支**尚未确认**。
- 参照项目 MAA 的成熟解法（`Python/asst/updater.py::_remove_stale_resource_files`）：**只清理 `resource/(tasks|template)` 白名单目录内的陈旧文件**，且带符号链接越界保护、大小写不敏感 `samefile` 判定、失败仅告警不中断。原注释写明理由："残留旧文件会导致资源加载失败（重名）"。
- MaaEOV 的框架加载是"目录全量扫描 + 同名静默覆盖"，残留 JSON 会引入幽灵节点（与 `verify_feature` 第 4 段的跨文件同名检测同一根因）。

### 2.3 实施步骤

**Step 1｜确认事实（0.5 人日，必须先做）**
1. 在干净环境准备两个目录：`A`（v1.14.7 完整包解压）、`B`（A 的副本，手工写入 3 个干扰文件：`resource/base/pipeline/_stale_test.json`、`resource/base/image/_stale.png`、`agent/_stale_test.py`）。
2. 用 `B` 作为用户目录，触发一次资源 OTA（指向当前发布版资源包）。
3. 记录更新前后 `agent/*.py`、`resource/base/pipeline/*.json` 的文件清单差异（文件名 + mtime + 大小）。
4. 判定矩阵：
   - `agent/` 被清空 → 走 Step 2 措施 A+B+C（最高危）；
   - `agent/` 保留但 `_stale_test.py` 残留 → 只走 B+C；
   - 全部被清理干净 → 只走 B（自检）+ 记录结论到 `docs/release.md`。
5. 结论写入 `docs/release.md` 新增章节「MFA 更新行为实测」，含清单快照。

**Step 2｜三道措施（1 人日）**
- **措施 A（发布侧，零代码）**：`scripts/build_resource_zip.py` 增加"包内清单生成"——输出 `resource/base/pipeline/.manifest.json`，内容为 `{文件名: sha256}`，同时写入 `agent/.manifest.json`。资源包**必须包含完整 `agent/`**（既有约定，固化为脚本断言：`agent/main.py` 不在包内则构建失败）。

  1. 读 `resource/base/pipeline/.manifest.json`，比对磁盘文件哈希，缺失/多余各记一条 WARN（**只报告，不删除**）；
  2. 校验 `agent/` 下 `main.py`、`soc_actions.py`、`auto_battle.py`、`crisis_mission.py`、`past_event.py`、`mfalog.py` 存在，缺失则 `mfa_err` 并在日志首行打印"资源包不完整，请重新下载完整包"；
  3. 自检耗时上限 300ms，异常一律 try/except 包裹，**绝不允许阻断 Agent 启动**。
- **措施 C（流程侧）**：`scripts/package_full.py` 与 `build_resource_zip.py` 增加版本一致性断言：`interface.json.version` == 包内 `resource/version.json`（若无则新建），不一致直接失败。

## 3. P0-2：非终端节点双出口（`timeout` + `on_error`）

### 3.1 目标
让"等待超时"从**静默成功/静默卡死**变成**显式失败 + 可定位**，把 **221 个真风险非终端节点**（见 0.5 校准 1）的 `timeout` 收敛到 0 缺口，并为关键链路加 `on_error` 诊断出口。

### 3.2 现状依据
- 316 / 356（88.8%）非终端节点未写 `timeout`，默认值 20000ms 在"等结算/等加载"场景必然提前掐断——v1.14.6「危机行动调令」假阴性（实测约 27s 报失败）即此根因，已在校验器第 9 段做了**局部**（扫荡链）拦截。
- **但 316 里只有 221 是真风险**：95 个的 `next` 含即时命中候选（`DirectHit`/无 `recognition`），扫描不会吃满 20s。典型反例：`_NavigateDailyMission`（7 个候选，全是需等待的识别节点，无 timeout）属真风险；而"识别 A → 点 B（DirectHit）"这类两跳结构不属。
- `agent/soc_actions.py:137` 在 `max_wait`（默认 540s）耗尽后 `return True`，pipeline 认为战斗结算完成 → **静默假成功**，后续节点在错误界面继续点击。

### 3.3 实施步骤

**Step 1｜先筛真风险，再定标（0.5 人日）**
0. **分类先行**（0.5 校准 1 的结论）：`next` 中存在即时命中候选（`recognition` 缺省 / `DirectHit`）的 95 个节点**不动**——它们的扫描在首个候选即返回，补 `timeout` 只增加噪音。真风险是剩余 **221** 个。

## 4A. P0-4：任务图静态护栏（移植 Maadori `check_closure`）

### 4A.1 目标
把"逃生链必须有第二出口 / 无死角自环 / 无悬空引用"从口头约定变成 **CI 红灯**。pipeline 是声明式的，图论错误在运行时表现为"卡住"或"超时"，事后极难定位——静态检查是唯一低成本手段。

### 4A.2 现状依据
- 本项目 `verify_feature.py` 第 5 段只查 **死链**（`next`/`on_error` 目标是否存在），不查**图论性质**（陷阱自环、终止可达性、无出边节点）。
- Maadori 的 `debug/check_closure.py` 已跑通同一套路：73 行、退出码 0/1/2、接入 CI，并在其计划中扩展为 `check_traps` + `check_termination`。
- 本仓库实测（严格判据）：自环 1、`on_error` 1、**陷阱 0** → 存量干净，**这不是存量修补，是零改造成本的回归护栏**。
- Maadori 同时给出了"已否决子检查"的反面经验：*"落点须在判据 ROI 内"* 在其库内 10 个节点中 9 个合法越界（判据区≠点击区），硬门禁噪声大于收益。**本项不采纳该子检查。**

### 4A.3 实施步骤
1. **抽公共层**：`scripts/pj.py` 提供 `load_nodes(dir) -> (nodes: dict, files: list)` 与 `strip_ref_prefix()`，`verify_feature.py` 改为调用它（消除第三份 `strip_jsonc` 实现）。

   - `check_dangling`：悬空引用（等价于 verify 第 5 段，保留以便独立运行）；

3. **判据复用**：`check_traps` 与 P0-2 的 `is_instant_match` 共用 `pj.py` 中的实现——**一个判据只写一份**，避免"校验口径与修补口径漂移"。
4. **退出码契约**：`0` 全绿；`1` 有 error；`2` 路径/加载错误（无文件）。`--strict` 时 warn 也算失败。
5. **注入测试**：`tests/test_graph.py` 三个内存构造图——陷阱图（期望 1）、正常重试图（期望 0）、悬空图（期望 1）。

## 10. 执行顺序与门禁

```
第 1 周：P0-3（工具 5 段） → P0-4（图论护栏 0.5d） → P0-5（测试底座 + 修 _parse_ticket）
第 2 周：P0-1 Step1 取证（OTA 实测） → Step2/3（自检 + 版本断言）
第 3 周：P0-6（取证流水线） → 接入三个痛点
第 4 周：P0-2 Step1 分类定标 → Step2 分批补 221 个 timeout（先 5 个大文件 = 160 个）
第 5 周：P0-2 Step3 修假成功 → Step4 关键链 on_error → 全量回归
第 6 周：P1-7 agent 包结构（借 P0-5 的测试护航）
第 7-8 周：P1-4 生成层（零变更基线 → 21 组抽取）
第 9 周：P1-5 纠错表 → P1-6 注释规范
待触发：P2-7（需前置实验）/ P2-8（需全量回归窗口）
```

**顺序原理（Maadori 校准后）**：
1. **先建网，再动大件**——P0-3/P0-4/P0-5 合计 4 人日，却能让后面所有改动"错了立刻知道"。
2. **pipeline 改造（P0-2/P1-4）放在 agent 改造（P1-7）之后**：agent 有测试后可安全重构，而 pipeline 改动必须靠实机回归，成本更高，宜在后段集中执行。
3. **P2-7/P2-8 保持待触发**：二者都依赖"未验证前提"（同名覆盖行为 / 框架 ABI 兼容），不做前置实验就不排期。

**每项完成的定义（DoD）**：
1. 代码/资源已合并到 master；
2. `verify_feature.py` = `ALL_OK` **且** `python -m pytest -q` 全绿（P0-5 之后生效）**且** `check_graph.py --strict` = 0（P0-4 之后生效）；
3. 受影响任务实机跑通 1 轮；
4. 本文档对应"可衡量目标"表格已回填实测值；
5. `resource/announcement/Changelog.md` 有用户可见的说明（若涉及行为变化）。
