# 认知海域（Sea of Cognition）重构方案

> 制定时间：2026-10-31　基线：`v1.16.0` / master `fee5dc1` + 本次 4 处 P0 修复
> 前置文档：`docs/认知海域可行性评估-2026-10-31.md`
> 原则：**先把"能跑"证明出来，再谈"跑得聪明"。** 任何阶段不允许在上一阶段未验收前开工。

---

## 0. 设计原则（先定调，后面所有取舍都按它判）

| # | 原则 | 反面案例（现有代码里的实际教训） |
|---|---|---|
| 1 | **探测零副作用** | `SoCResume` 13 个探测项都带 `Click`，识别一偏就盲点坐标 |
| 2 | **状态归 Python，流程归 JSON** | MaaFramework 无跨节点变量、无循环计数器 → 选过哪张卡只能塞进 CustomAction |
| 3 | **判定集中，路由分散** | 同一件事（"现在在哪"）写死在 13 个节点的识别参数里，无法复用、无法测试 |
| 4 | **宁可停下留证，不要盲点** | `SoCInspirationFallback` / `SoCDeepDiveFallback` 固定点 `[351,581]`，点错比停下更难查 |
| 5 | **数据外置，热更不改码** | 5 张 Buff 优先级写在 `interface.json` 的 doc 字符串里，用户看不到也用不上 |
| 6 | **每阶段可回滚，每阶段可验收** | 一次性重写 → 出问题无法定位是哪一步引入的 |

## 1. 现状诊断

### 1.1 规模与结构

- 单文件 `认知海域.json`：895 行 / 34 节点，注释约占一半，多轮决策层层堆叠。
- `agent/soc_actions.py`：332 行 / 2 个 CustomAction，与 `auto_battle._parse_param` / `_screencap` 隐式耦合。
- 无状态对象、无数据层、无测试。
- 至今**未实机跑通过一次**（`debug/maafw.log` 无 `#SeaOfCognition` 的 `Tasker.Task.Starting`）。

### 1.2 四类结构性缺陷

**A. 探测即动作（最大风险）**

```
SoCResume (DirectHit) next: [SoCClaim, SoCContinue, SoCStartBattle, ... ×13]
```

每个探测节点自带识别 + 动作。命中即点击。问题：
- `SoCClaim` 用全屏 OCR 找 `[领取]|[确认]`，排在**第 1 位** → 任何带"确认"的弹窗都会误点。
- 探测项无法安全排序（调顺序 = 调点击优先级）。
- 无法回答"现在到底在哪个阶段"这个最基本的问题。

**B. 判定碎片化**

同一个"这是战斗结算屏吗"，在 `SoCResume` / `SoCContinueDive` / `SoCAfterContinue` 三处各写一遍识别参数。改一处漏两处。

**C. 状态完全缺失**

- 不知道已选几张全局 Buff（只知道"未激发"标签没了）。
- 不知道打到第几个节点、当前积分、剩余券。
- 无法"接着上次跑"，`SoCResume` 只能靠界面外观倒推。

**D. 无验证手段**

改一次 pipeline → 重载资源 → 跑一遍 → 看日志，反馈环 1–3 分钟。没有离线用例，没有基线可比对。

## 2. 目标架构

```
┌─────────────────────────────────────────────────────────────┐
│ L1 流程层  resource/base/pipeline/SeaOfCognition/*.json      │
│    只表达「点哪、走哪」；不判阶段、不做决策                    │
├─────────────────────────────────────────────────────────────┤
│ L2 状态层  agent/soc/status.py                               │
│    SoCStatus 单例：阶段 / 层 / 已选 Buff / 节点序号 / 积分 / 券 │
│    进程内全局变量 + debug/soc_state.json 落盘                 │
├─────────────────────────────────────────────────────────────┤
│ L3 决策层  agent/soc/phase.py（判阶段） policy.py（选什么）    │
│            资源：resource/base/data/soc/*.json               │
│    纯函数优先：输入 (观测, 状态)，输出 (阶段 / 分值 / 动作)     │
└─────────────────────────────────────────────────────────────┘
```

**关键点**：L1 只留"确定性的点击序列"，一切"需要判断"的都下沉到 L2/L3。这是 MaaFramework 表达力下的最优分工，也是 MAA 肉鸽"流程 JSON + 插件 Python + 数据 JSON"三件套在 MaaEOV 上的等价实现。

### 2.1 核心机制：单节点阶段判定 + `override_next`

MaaFramework 提供 `context.override_next(node_name, [...])`，可以在 CustomRecognition 内部**动态改写当前节点的 next**。据此把 13 个探测节点压成 1 个：

```jsonc
"SoCDetectPhase": {
    "recognition": {
        "type": "Custom",
        "param": { "custom_recognition": "SoCPhase" }
    },
    // 静态 next 必须写全（check_graph 要能过死链检查），
    // 实际运行时由 Python 用 override_next 裁成单项。
    "next": [
        "SoCStage_Claim", "SoCStage_Settle", "SoCStage_GB",
        "SoCStage_InBuff", "SoCStage_Battle", "SoCStage_DiveChoice",
        "SoCStage_NodeMap", "SoCStage_LayerSelect", "SoCStage_Team",
        "SoCStage_Home", "SoCFallbackStart"
    ]
}
```

Python 侧：

```python
def analyze(context, argv):
    phase = classify(argv.image)          # 一次分类，八个特征
    status.set_phase(phase)
    if phase is None:
        return None                        # 落到 SoCFallbackStart
    context.override_next(argv.node_name, [STAGE_ENTRY[phase]])
    return CustomRecognition.AnalyzeResult(box=FEATURE_BOX[phase], detail=phase)
```

收益：
- 探测零副作用（Python 只读图，不点）。
- 阶段判定是一个**纯函数**，可以用固定截图做单元测试。
- 新增界面类型 = 在 `phase.py` 加一条特征，pipeline 不改。

代价：
- 静态图分析（`check_graph` 的可达性）会变乐观 —— 静态 next 全写，运行时只走一条。**死链检查仍然有效**，只是"哪些分支真的会被走到"要靠实机报告。

## 3. 模块划分与职责

### 3.1 Pipeline（6 个文件）

```
resource/base/pipeline/SeaOfCognition/
├── _Entry.json       #SeaOfCognition 入口、SoCDetectPhase、SoCFallbackStart、SoCDone
├── _Nav.json        BCR 导航（只包一层，复用 Shared 的 _NavigateBCR 等）
├── _Dive.json       选层 → 开始/继续下潜 → 下潜方式 → 配队
├── _Buff.json       全局 Buff 选卡 + 局内 Buff 二选一
├── _Battle.json     开始作战 → 战斗等待 → 结算继续
└── _Result.json     领奖 → 券尽 → 结束
```

拆分规则：
- 节点名全局唯一（`verify_feature` 对跨文件同名判 FAIL，必须守住）。
- 跨文件只允许引用 `_Entry.json` 和 `Shared.json` 里的节点，避免环状依赖。
- 每个文件头部保留"这个文件负责什么 / 不负责什么"的一句话说明。

### 3.2 Agent（`agent/soc/` 子包）

```
agent/soc/
├── __init__.py     统一 import 触发注册
├── const.py        全部 ROI / 坐标 / 阈值常量（唯一真源）
├── status.py       SoCStatus 单例 + 落盘/读回
├── phase.py        CustomRecognition「SoCPhase」阶段判定
├── actions.py      CustomAction：SoCAwaitBattle（迁入）、SoCBuffPick（全局选卡）
├── policy.py       纯函数：buff 打分、节点打分、是否该停
├── nodes.py        （P6）节点图识别 CustomRecognition「SoCNodeMap」
└── data.py         读取 resource/base/data/soc/*.json，带默认值兜底
```

`actions.py` 只做"读图 → 决策 → 点"，决策本身调 `policy.py`。这样 `policy.py` 可以纯单测，不需要设备。

### 3.3 数据

```
resource/base/data/soc/
├── buff_priority.json    {"global":[{name,score,keywords}], "in_battle":[...]}
├── layers.json           {"梦渊层":{ocr:[...], expect_score:355, priority:3}, ...}
└── nodes.json            （P6）{"battle":30,"elite":45,"event":20,...}
```

照抄 `level_groups.json` 的做法：**单一数据源 + 校验脚本反查一致性**。

## 4. 数据流

### 4.1 一次完整运行

```
启动
 └ SoCDetectPhase ──判阶段──> Stage_Entry
      │                         │
      │                    ┌────┴────┐
      │              导航/下潜    已在局内
      │                    │         │
      └────────────────────┴────┬────┘
                                 ▼
                        ┌── 节点循环 ──┐
                        │  Buff 选择    │  ← status.gb_picked / in_bf_picked
                        │  开始作战     │  ← status.battles_done++
                        │  战斗等待     │  ← status.score / tickets 更新
                        │  结算继续     │  ← phase 重新判定
                        └──────┬───────┘
                               ▼
                        结算屏 → 领奖 → status.rounds++
                               │
                        券尽？ ─是→ SoCDone（落盘最终状态）
                               └否→ 回 Stage_Entry
```

### 4.2 每次状态变更都落盘

`status.save()` 在四个时机调用：进入新阶段、选完一张 Buff、战斗结算、轮次结束。文件 `debug/soc_state.json`：

```json
{"run_id":"20261031-2210","layer":"梦渊层","phase":"battle",
 "node_step":3,"gb_picked":["能量涌流","战前准备"],"in_bf_picked":["激流"],
 "battles_done":2,"score":710,"tickets_left":3,"rounds":1,
 "started_at":1761923400.0,"errors":[]}
```

作用：
- 崩溃/停止后重启，`SoCDetectPhase` 可以先读状态，再用界面校验，两者一致才续跑。
- 事后复盘：这一轮到底选了什么、打了几个节点。

## 5. 任务状态与流转规则

### 5.1 阶段枚举（8 个）

| phase | 含义 | 判定特征（模板 / OCR） | 阶段入口 |
|---|---|---|---|
| `home` | 游戏主界面 | `~Homepage`（Shared 复用） | Stage_Home |
| `nav` | BCR 界面 | `认知海域图标.png` | Stage_Nav |
| `layer` | 选层界面 | `开始下潜` / `继续下潜` 按钮 | Stage_Layer |
| `dive` | 下潜方式二选一 | `深潜指引` / `自由探索` 卡 | Stage_Dive |
| `team` | 配队界面 | `进入海域.png` | Stage_Team |
| `gb` | 全局 Buff 选择屏 | `剩余可选灵感` / 灵感节点卡 | Stage_GB |
| `inbuff` | 局内 Buff 二选一 | `请选择一个短暂灵感` 标题 | Stage_InBuff |
| `battle` | 战斗页 / 结算 | 开始作战 / 战斗完成继续 | Stage_Battle |
| `settle` | 领奖 / 结果 | `领取` / `确认` 弹窗 | Stage_Claim |

> 判定顺序固定为「**越靠"结果"越优先**」：settle > battle > inbuff > gb > team > dive > layer > nav > home。理由：结算类界面上可能残留上一屏的元素，反向排序会误判成上一阶段。

### 5.2 流转规则（硬约束）

1. **任何阶段只能由 `SoCDetectPhase` 进入**，阶段内部用普通链推进，不再回头调判定。
2. **阶段内失败 → 回到 `SoCDetectPhase` 重新判定**，不做局部重试猜测。
3. **`SoCDetectPhase` 连续 3 次返回 `None` → `_StopTask` + 取证**，不再回落 `SoCFallbackStart` 盲闯。
4. **`status.phase == done` 时直接结束**，不再判屏。
5. **轮次上限**：`status.rounds >= 3`（可配）→ 强制结束，防券数读错导致无限刷。

### 5.3 与现有节点的映射

| 现有节点 | 去向 |
|---|---|
| `SoCResume` | 改造成 `SoCDetectPhase`（去掉全部 action） |
| `SoCClaim` / `SoCContinue` / `SoCStartBattle` / `SoCInBattleBuff*` / `SoCInspirationNode*` / `SoCState_GB0/1` / `SoCContinueDive` / `SoCDeepDive*` | 拆成「判定」（入 `phase.py`）+「动作」（入各 Stage 入口） |
| `SoCFallbackStart` | 保留，但仅作 `SoCDetectPhase` 返回 None 时的显式兜底（且只允许 1 次） |
| `SoCInspirationFallback` / `SoCDeepDiveFallback` | **删除**（盲点坐标） |
| `SoCNodeLoop` / `SoCAfterContinue` | **删除**（判定职责已归 `phase.py`） |
| `_SoCGBAbandonConfirm` | 保留（弹窗兜底有效） |

## 6. 关键依赖与接口约束

### 6.1 MaaFramework 硬约束（踩过的坑，必须遵守）

| 约束 | 说明 | 来源 |
|---|---|---|
| `custom_action` 必须嵌在 `action.param` 内 | 写在顶层不报错但**不执行** | 本次修复，全库 15 个动作只错 1 个 |
| `run_recognition("OCR", img)` 返回 None | 参数必须是**节点名**或改用 `run_recognition_direct(JRecognitionType.X, JXxx(...), img)` | `past_event.py` 注释 / 踩坑 #3 |
| `context.tasker.stopping` 是属性不是方法 | — | `soc_actions.py` 已在用 |
| 每个节点显式写 `timeout` | 扫描窗口 = pretask 的 timeout；不写回退 ~20s | `verify_feature` 第 12 段 |
| `next` 按识别命中顺序推进，**不看 action 返回值** | action 返回 False = 节点失败走 `on_error` | 本次更正 |
| `DirectHit` 排首位 = 后续项永不可达 | — | 本次更正 |
| 无循环计数器 / 无跨节点变量 | 状态只能进 Python | 项目记忆 |

### 6.2 校验工具的迁移前置

**当前 `pj.load_pipelines` 与 `verify_feature` 都用 `os.listdir`，只扫一层。** 拆子目录或 `agent/soc/` 子包后，两者会静默漏扫 → 校验全绿但什么都没检查。

必须在 Phase 1（拆文件之前）完成：
- `pj.load_pipelines` 递归一层子目录，返回值保留 `"子目录/文件名"` 作为 key。
- `verify_feature` 的 agent 扫描递归 `agent/**/*.py`。
- 跨文件同名检查照旧（递归后覆盖面变大，可能暴露既有冲突，需先修）。

### 6.3 Agent 侧接口

| 接口 | 用途 | 注意 |
|---|---|---|
| `context.override_next(node, [..])` | 动态路由 | 目标节点必须在静态 next 或全局存在，否则运行时 `invalid node id` |
| `context.override_pipeline({...})` | 临时改识别参数 | 作用于整个 task 上下文，用完要还原或用 `context.clone()` |
| `argv.image`（CustomRecognition） | 框架已截好的图 | 优先用它，少截一次屏 |
| `argv.reco_detail`（CustomRecognition 兜底用） | 直接读识别结果 | 避免二次 OCR（`crisis_mission.py` 范式） |
| `context.tasker.stopping` | 用户急停 | 所有轮询循环必须检查 |

图像能力：**只有 numpy**，无 cv2 / PIL / onnxruntime。写图用 `agent/imaging.imwrite`（内置 PNG 编码器）。

## 7. 异常与边界处理

### 7.1 三级分类

| 级别 | 判据 | 处理 | 是否继续 |
|---|---|---|---|
| **L1 可重试** | 界面加载慢、动画未结束、识别分数 0.5–0.8 | 等待 + 重判，最多 3 次（间隔 1s 递增） | 是 |
| **L2 可降级** | 某张 Buff 卡名 OCR 失败、节点类型未知 | 记录到 `status.errors`，用中性策略继续（未知卡按最低分处理但仍选） | 是 |
| **L3 必须停** | 连续 3 次判不出阶段、战斗超时、券数读成非法值 | `_StopTask` + `debug/evidence/` 存整屏 + 元数据 | **否** |

### 7.2 具体边界

| 场景 | 处理 |
|---|---|
| 中途已有进行中的海域 | 判定为 `layer` 阶段但按钮是「继续下潜」→ 走 Continue 分支，**不弹二选一** |
| 当期已跑满 1000 分 | `SoCAwaitBattle` 读左下角积分 == 1000 → 记 `status.done=true` → 领奖后直接结束，不再开新一轮 |
| 入场券不足 | 任意阶段识别到「入场券不足」→ `status.tickets_left=0` → 走 `SoCDone` |
| 全局 Buff 一张都选不到 | 不认为是失败：点「继续」→ 弹「是否放弃激发」→ 点 ✓ → 重试一轮；累计 2 次仍未选到则记录并放弃选卡直接进战斗 |
| 局内 Buff 只点了一张就进战斗 | 视为可选（游戏允许），不判失败 |
| 结算空白页 / 奖励弹窗乱序 | 沿用现有 `SoCAwaitBattle` 轮询（`init_wait + poll + max_wait`），不改成模板死等 |
| 用户中途点停止 | 所有 CustomAction 轮询内检查 `tasker.stopping`，立即返回 False 并落盘状态 |
| 模拟器断连 | 依赖 `RetryOnDisconnected`，SoC 层不额外处理 |

### 7.3 绝对禁止

- 任何固定坐标点击（`DirectHit + target`）。现有 3 处全部移除。
- `while True` 循环无上限。所有轮询必须带 `max_wait` / `max_iter` / `wall_cap`。
- 识别不到时"点一下试试"。识别不到就是识别不到，停下留证。

## 8. 分阶段实施

> 每阶段独立 commit + tag（`soc-p0` … `soc-p6`），可单独回滚。
> **每阶段验收不通过，不允许进入下一阶段。**

### Phase 0 · 基线固化（0.5 人日）

| 项 | 内容 |
|---|---|
| 目标 | 拿到"现在的真实行为"作为后续所有回归的对照基线 |
| 影响范围 | **不改代码**。只跑 + 采图 |
| 动作 | ① 单跑 `#SeaOfCognition`，全程录屏；② 采 9 个阶段界面截图 → `tests/fixtures/soc/<phase>.png`；③ 保存 `debug/task_runs/report_*.json` |
| 验收 | ① `mfa_agent.log` 出现 `SoC gb_pick START`（证明 P0-1 修复生效）；② 9 张 fixture 齐全且能人工辨认；③ 有一份跑通的节点序列 JSON；④ 若跑不通，记录卡在第几个节点 |

**若 Phase 0 跑不通**：立刻停下，按报告定位。阶段 0 的唯一价值就是"知道现在在哪"，拿不到就说明还有未发现的阻断点，带着它往下走会把问题埋进重构里。

### Phase 1 · 护栏先行（1 人日）

| 项 | 内容 |
|---|---|
| 目标 | 让校验工具能覆盖子目录和子包；建立 SoC 专用静态检查 |
| 影响范围 | `scripts/pj.py`、`scripts/verify_feature.py`、`scripts/check_graph.py`、新增 `scripts/check_soc.py`。**不动 pipeline、不动 agent 运行时** |
| 动作 | ① `load_pipelines` 递归一层；② agent 扫描递归；③ `check_soc.py`：阶段节点与 `phase.py` 枚举一致性、状态字段完整性、数据 JSON 可解析、禁止 `DirectHit+target`、每个 Stage 入口必须可从 `SoCDetectPhase` 到达 |
| 验收 | ① 递归改造后 `verify_feature` 仍 `ALL_OK`（或暴露的既有问题已确认为噪声）；② `check_graph --strict` 退出码 0；③ `check_soc.py` 对当前代码输出 PASS，故意塞一个 `DirectHit+target` 后变 FAIL |

### Phase 2 · 状态层（1 人日）

| 项 | 内容 |

### 13.7 收尾链路：完成后必须返回主界面

**问题**：任务结束在选层界面（认知海域内部）。后续任务（清体力、补给站、外部招募…）全部假设从主界面开始，停在这里会让下一个任务直接失败。

**实现**（新增 2 个节点）：

```jsonc
_SoCScoreFull   (OCR 左下角 1000/1000)  → _SoCReturnHome
_SoCNoTicket    (OCR 入场券不足)         → _SoCReturnHome
_SoCBackToLayer (OCR 右下 开始下潜)      → [_SoCScoreFull, SoCStartDive]   ← 分流
_SoCReturnHome  (复用 _NavigateHomepage) → ~SoCHome → SoCDone
```

关键分流：**`_SoCBackToLayer` 不能直接收尾**。一层只有 500 分，满额需 2 轮——第一轮结束必须继续下潜，只有读到底部 `1000/1000` 才回主界面。否则跑一轮 500 分就收工，永远拿不满。

`_SoCReturnHome` 直接复用 Shared 的 `_NavigateHomepage`（含返回键、各类弹窗兜底），并挂了 `on_error: [SoCDone]`——退不出去不判失败（奖励已入账），交给下一个任务自己导航。

**顺带解决了一个跨天问题**：04:09 实测遇到「注意 · 新的一天开始了，是否要跳转至签到？」弹窗。`_NavigateHomepage` 链里的 `_CancelGeneral` 能直接关掉它，无需新增节点。

**实测**：

```
从选层界面启动：16.5s  SoCResume → _SoCScoreFull → _SoCReturnHome → _CancelGeneral → _HomeButton → ~Homepage → ~SoCHome → SoCDone
从主界面启动  ：28.0s  … → SoCAtBCR → SoCEntryCognition → _SoCScoreFull(1000/1000) → _SoCReturnHome → … → SoCDone
```

### 13.8 进行中的下潜：直接放弃重开（不做续跑）

**界面形态**（实机 2026-11-01 04:19 确认）：

| 状态 | 选层界面右下角 |
|---|---|
| 无进行中 | 只有一个「开始下潜」 |
| **有进行中** | **「终止下潜」+「继续下潜」**，下方还有「探索进度 N/14」 |

**设计决策：放弃重开，不续跑。**

| 理由 | 说明 |
|---|---|
| 状态不可知 | 续跑时局内已选 Buff、已打节点、剩余灵感我们都无记忆，接上去大概率错乱 |
| 代价不对称 | 单轮仅 8–19 分钟，重开比"接错"便宜得多 |
| 顺便清场 | 把上次任务中途失败留下的烂摊子清干净，每次从确定状态开始 |

**放弃三步链**（新增 3 个节点，共 44 个）：

```jsonc
_SoCAbandonDive    (OCR 终止下潜)              → 点击按钮
_SoCAbandonConfirm (OCR 是否放弃本次探索)      → 点 ✓[732,407]
_SoCAbandonResult  (OCR 探索终止／完成节点)    → 点 [640,360] → [_SoCScoreFull, SoCSelectLayer]
```

注意 `_SoCAbandonResult` 的终点不是直接重开——**先判满分**：已满就走 `_SoCReturnHome`（不留进行中的垃圾状态），未满才 `SoCSelectLayer` 重新选层开始。

**顺序**：`_SoCAbandonDive` 排在 `_SoCScoreFull` 之前。先清理再判分，保证退出时状态干净。

**实测**（21.0s，无一次重试）：

```
SoCResume → _SoCAbandonDive(终止下潜 0.9973) → _SoCAbandonConfirm(是否放弃本次探索 0.982)
→ _SoCAbandonResult(完成节点 0.9999) → _SoCScoreFull(1000/1000 0.9993)
→ _SoCReturnHome → _NavigateHomepage → _HomeButton → ~Homepage → ~SoCHome → SoCDone
```

> `SoCContinueDive`（模版「继续下潜」→ 续跑）保留为兜底：只在放弃链识别失败时才会命中。正常路径不该走到它。

### 13.9 灵感（Buff）选择配置化

**改造前**：全局灵感「见卡就点最左一张」、局内灵感「永远点左卡」，完全不看内容。想按队伍强度调整策略，必须先让程序读得出卡名。

**两档配置**（`interface.json` → 「认知海域-Buff配置」）：

| 配置 | 实现 | 风险 |
|---|---|---|
| **配置一（默认）** | `mode="left"`：全局取最左、局内点左卡，**不读卡名**，与原行为完全一致 | 零新增风险 |
| **配置二（低配稳健）** | OCR 读卡后按优先级表打分选最高；全局 应急护盾 > 身心调和 > 环境遮蔽 > 战前准备 > 能量涌流，局内优先护盾/减伤/回复 | 依赖 OCR 稳定 |
| 配置三（极限保命） | 数据已写入 `p3`，**GUI 暂不暴露**（避免"选了没效果"的空壳选项） | — |

权重表：`resource/base/data/soc/buff_priority.json`，改数据即生效，不动代码。

**两个必须记住的技术坑：**

1. **`RecognitionDetail` 没有 `.detail` 字段。**
   正确结构是 `all_results: list[RecognitionResult]` / `best_result` / `raw_detail`，OCR 项是 `OCRResult(text, box, score)`。
   按 `r.detail["all"]` 取文本永远拿到 None——实测卡名连续三次全部「未读出」才定位到。

2. **Buff 界面布局不稳定。**
   同一期里见过两种：横排小卡（「未激发」在卡片正下方，标题在标签上方约 137px）和竖排大卡（「未激发」在卡片右下角，标题在卡片中部，相对方向完全变了）。
   固定偏移 ROI 必然读错。最终方案：**以标签为中心取「一卡宽 × 上下 400px」区域，读整张卡的文字（标题+描述）**，用关键词打分。描述里一定含「护盾/治疗/攻击/破甲」，比只认 4 字标题鲁棒得多。

**实测（配置二，2026-11-01 05:17）：**

```
全局 #1 〔…身心调和… 分=80〕          ← 生存类得分正确
全局 #3 〔…神秘陌客… 分=15〕          ← 未知卡走保底分
局内 左[眩晕…]=40 / 右[警戒伤害+20%…]=55 → 选右
局内 左[攻击无视目标4…]=60 / 右[替补栏+1…]=55 → 选左
```

**已知局限**：整卡 OCR 仍可能读到紧邻卡片的文字（实测日志里出现过混串），已把横向范围收到 ±85px 并排除「未激发」等标签词。权重是拍脑袋填的，**没有失败样本校准**——等有战斗失败截图后按实际死因调整。

### 13.10 入场券不足 2 张 → 收尾结束

**阈值为什么是 2**：一层只有 500 分，打满 1000 需要 **2 轮 = 2 张券**。券只剩 1 张时开新一轮必然打不满，白亏一张券加 8–19 分钟。

**实现**：`_SoCTicketLow`（CustomRecognition「SoCTicketLow」）读选层界面右上角券数，`< 2` 命中 → `_SoCReturnHome` → 回主界面结束。

**挂载位置只有 3 处，且都在选层界面**：`SoCEntryCognition`（第 3 位）、`SoCSelectLayer`（第 2 位）、`_SoCBackToLayer`（第 2 位）。
**故意不挂 `SoCResume.next`**——主界面右上角是资源数（20,180），实测会被误读成 `201`。虽然 201 ≥ 2 不会误判，但这个信号本身不可靠。

**技术难点：券数只有 18px 高，直接 OCR 读不出（返回空）。**
最终做法：把该区域裁出来 `np.repeat` 放大 4 倍再送 OCR，才读得出。
实测日志：`券数读数=9（阈值 2，OCR='B 9'）`——券图标被误认成 `B`，数字提取正确即可，不需要文本干净。

**关于"弹出说明"**：MaaFramework **没有让 agent 主动弹 GUI 通知的接口**（`NotificationType` 是 EventSink 回调类型，通知只由框架在任务开始/失败/完成时触发）。
所以说明落在两处：节点 `focus` 文案（GUI 进度条显示「入场券不足 2 张 → 无法打满，收尾结束」）+ `mfa_agent.log` 的完整原因记录。
