# interface 任务清单审查与精简方案

> 日期：2026-10-21
> 基线：MaaEOV v1.14.7，`interface.json` 19 个任务 / 608 个 pipeline 节点
> 方法：以"任务入口 + 该任务所有 option 的 `pipeline_override` 注入点"为起点做 BFS，得到每个任务的**可达节点集**；再剔除"启动游戏"可达的通用前缀，得到**任务专属集**，在专属集上算交集。

---

## 0. 结论

**19 项 → 13 项（推荐方案 A），删除 6 个冗余入口，合并 9 项为 3 项。**

| 合并组 | 现状 | 精简后 | 共享节点 | 风险 |
|---|---|---|---|---|
| 领取类 | 领取邮件 / 领取任务奖励 / 领取应对协议 / 活动-每日行动补给 / 活动-短期支援补贴（5） | **一键领取**（1） | 3 | 低 |
| 活动类 | 当期活动 / 往期活动（2） | **活动作战**（1） | 8 | 中 |
| 周常类 | 每周-阈限禁区 / 联线封锁（2） | **周常挑战**（1） | 8 | 中低 |

**重要前提（务必先读）**：合并的收益主要是**用户侧任务列表与操作步数**，**不是**代码量。三组合计只去重 19 个节点（672 个"任务专属节点占用"里占 2.8%），因此**不会显著减轻 P0-2 的 221 个 timeout 补写工作量**（估算仅省 6–9 个，3–4%）。它应作为**独立的产品迭代**排期，不与 P0 改造混在一起。

## 1. 度量基线（可复现）

| 指标 | 实测 |
|---|---|
| 任务数 | 19 |
| pipeline 节点总数 | 608 |
| 通用前缀（从"启动游戏"入口可达） | **67**（占 11%）—— 启动、维护、断线重连、回主页等所有任务共用 |
| 各任务专属节点之和 | 672 |
| 专属节点去重并集 | 541 → **跨任务重复占用 131 个（19.5%）** |
| 重叠集中度 | 高度集中在 5 组，其余两两交集 ≤ 5 节点 |

各任务专属集规模（降序）：清体力 166、危机行动调令 88、补给站 55、事务所 49、往期活动 46、每周-阈限禁区 42、认知海域 41、自动推图 40、领取应对协议 23、联线封锁 21、市区巡逻 20、外部招募 20、领取任务奖励 15、当期活动 15、活动-每日行动补给 12、活动-短期支援补贴 11、领取邮件 6、退出游戏 2、启动游戏 0。

## 2. 逐组评估

### 2.1 领取类 5 → 1：**建议合并**

**证据**
- 五项共享节点仅 3 个（`_EventFromHome` / `_NavigateEvent` / `~Event`），**并集 64 vs 各自合计 67**。
- 五项**都没有 option**（纯开关式任务），用户要在一键执行里勾 5 个条目、排 5 次顺序。
- 语义高度一致：进对应界面 → 点领取 → 返回主界面。差别只在"进哪个界面"。

**合并后范围**
`一键领取` = 领邮件 + 领任务奖励 + 领应对协议 + 活动-每日行动补给 + 活动-短期支援补贴。
内部结构建议：入口 `#一键领取` → `next` 依次挂 5 条子链，**全部用 `[JumpBack]`**，让每条子链结束后回到主界面再进下一条；末尾一个 DirectHit 终止节点。这样**单条子链失败不阻断后续**（这是合并最大的技术风险，必须用跳回而非串行）。

**option 设计**：1 个多选 `领取范围`（5 个 case，默认全选）。比现在 5 个独立任务的开关更少点击。

**收益 / 风险**
- 收益：任务列表 -4 项；用户每轮少勾 4 次、少排 4 次序；节点去重 3 个。
- 风险：低。唯一风险是"一键全领"会把用户不想领的东西也领了（如活动补给有每日上限，重复跑会空转）→ 用多选默认值 + 幂等设计（识别"已领取"直接跳过）化解。

**工作量**：0.5 人日 + 1 轮实机。

### 2.2 活动类 2 → 1：**建议合并，但保留两条导航支路**

**证据**
- 交集 8 个：`点击出发`、`点击快速完成`、`点击确定`、`行动力判定`、`行动次数确定`、`~等待快速完成结果`、`返回主界面`、`退出关卡详情页` —— **完整的"打活动关 + 结算"链**。
- 往期活动 46 节点 vs 当期活动 15 节点：往期多出的 31 个节点几乎全是"期次选择/翻页"导航。

**合并后范围**
`活动作战` = 进入活动页 → 选期次（当期/往期）→ 选关 → 打 → 结算。
`当期活动` 与 `往期活动` 变成同一入口下的两条导航支路，公共战斗链只保留一份（现在靠"两边各自写一遍同名节点"实现，靠 `verify_feature` 第 4 段保证不冲突）。

**option 设计**：`期次`（当期 / 往期 / 两者依次），往期分支再挂原有「选择往期活动」。

**收益 / 风险**
- 收益：任务列表 -1；共享链路合并后省 8 个节点（其中 3 个是等待型节点，可省 3–4 个 timeout 补写）。
- 风险：**中**。往期的期次选择逻辑复杂（31 个节点），合并后 entry 的 `next` 会变成两条支路并列，首匹配胜出——若两期次界面模板相似，可能误入。缓解：两支路首节点用**互斥 ROI + 高阈值**，并在校验器里加"同层支路 ROI 不得重叠"提示。

**工作量**：1 人日 + 2 轮实机（当期、往期各一轮）。

### 2.3 周常类 2 → 1：**建议合并**

**证据**
- 交集 8 个：`_BCRFromHome`、`_NavigateBCR`、`~BCR`、`_NavigateSystem`、`_SystemFromHome`、`_SweepFromLevel`、`_SweepConfirm` —— 都是 BCR（资源筹备）与扫荡链。
- 两者语义同属"每周限次挑战"，均在系统/BCR 界面内。

**合并后范围**
`周常挑战` = 阈限禁区 + 联线封锁 两段，各带独立跳回；公共的 BCR/扫荡链只留一份。
**option**：原 3 个选项（阈限禁区-选择关卡、阈限禁区-体力不足时使用体力道具、放弃未完成的联线封锁挑战）保留，外加一个"执行范围"多选。

**收益 / 风险**
- 收益：任务列表 -1；去重 8 节点（约省 2–3 个 timeout 补写）。
- 风险：中低。两者都能独立失败，用 `[JumpBack]` 串联即可；但阈限禁区有"体力不足用道具"分支，与联线封锁无体力消耗冲突，需在合并后明确顺序（建议阈限在前）。

**工作量**：0.5 人日 + 1 轮实机。

### 2.4 市区巡逻 + 领取任务奖励：**可合并，列为方案 B**

**证据**：交集 5 个（`_MissionFromHome`、`_NavigateMission`、`~Mission`、`_CloseWindows`、`_CloseMutualAid`），占较小集 33%。

**判断**：语义上是"做任务（巡逻）→ 领任务奖励"的天然闭环，用户通常连着跑。但它与 2.1 的"一键领取"重叠（领取任务奖励已在其中），若合并会造成**归属二义**。
→ 建议：**只做方案 B 时**才把「市区巡逻 + 领任务奖励」设为「日常任务」；默认方案 A 保持两者独立，避免一条链过长（单点失败影响面大）。

### 2.5 清体力 + 自动推图：**不建议合并（实测零重叠）**

**证据**：两者专属集交集 **0**。清体力是"选关 → 刷到没体力 → 用道具"，自动推图是"逐关推进 → 判完成 → 换下一关"，节点、option、失败语义都不同。

**判断**：合并只会把两个入口塞进一个任务，**不省一个节点**，还让用户多点一步选模式。保留独立；若嫌命名含糊，改名为「刷本（清体力）」与「推图（关卡推进）」即可。

### 2.6 其余 6 项：**不建议合并**

| 任务 | 理由 |
|---|---|
| 启动游戏 / 退出游戏 | **bookend（首尾）语义**，与业务任务正交。二者专属集分别为 0 / 2，已是"公共前缀 + 收尾"的正确形态。合并会让"只想启动不跑任务"的场景失效 |
| 危机行动调令 | 与 BCR 深度耦合（88 专属节点），且是独立玩法；与清体力有 81% 包含度但共享的是 BCR 基础设施，非任务逻辑 |
| 事务所（解读仪式） | 4 个 option 的独立系统，49 专属节点，无重叠对象 |
| 补给站 | 5 个 option 的独立系统，55 专属节点 |
| 外部招募 | 独立，20 专属节点 |
| 认知海域（开发中） | 独立玩法，41 专属节点；开发中不宜动入口 |

## 3. 对整体进度的影响

| 影响面 | 变化 | 量化 |
|---|---|---|
| P0-2（221 个 timeout） | **几乎无减负** | 合并只去重 19 节点 → 估算少补 6–9 个（3–4%）。**不能拿合并当省工手段** |
| P1-4（107 组同构） | 无直接影响 | 分组口径是"节点自身字段"，与任务归属无关 |
| P0-5 / P1-7（agent） | 无影响 | 不涉及 agent |
| 发布风险 | **上升** | 9 项合并为 3 项，涉及 3 个新入口 + 全部相关 option；需要 3 轮实机 + 一次灰度 |
| 用户习惯 | **有破坏性变更** | 任务名与条目数变化，需在 Changelog 明确"原 X 现并入 Y" |
| 工作量占用 | 约 **2 人日 + 4 轮实机** | 相当于 P0 全部工作量（约 15.5 人日）的 13%，且不能与 P0 并行改同一批 pipeline 文件 |

**排期建议**：放在 **P0-2 完成之后、P1-4 之前**的独立迭代。原因：合并会改动 `CollectRewards.json`、`CountermeasureProtocol.json` 等 5 个文件，与 P0-2 的批量补 timeout 改同一批文件，并行会互相污染 diff。

## 5. 若执行方案 A：实施步骤与验收

1. **建聚合入口（0.5 人日）**：新增 `Shared.json` 之外的聚合文件（建议 `Aggregated.json`，避免污染 Shared 的通用库语义），写 3 个入口节点 `#一键领取` / `#活动作战` / `#周常挑战`，用 `[JumpBack]` 串子链，末尾 DirectHit 终止。
2. **改 interface（0.2 人日）**：19 项 → 13 项；迁移原有 option（键名不变，避免 `pipeline_override` 目标失效）；新增「领取范围」「期次」「执行范围」3 个 option。
3. **补 timeout 与 on_error（0.3 人日）**：3 个新入口节点的 `timeout` 必须覆盖下游最长等待；每条子链的**第一个识别节点**补 `on_error` → 回主界面，防单链失败卡死。
4. **校验与回归（1 人日）**：
   - `python scripts/verify_feature.py` = `ALL_OK`（第 3 段会核对新 entry 存在、新 option 已定义）；
   - `python scripts/check_graph.py --strict` = 0（新入口的终止可达性）；
   - `python -m unittest discover -s tests` 全绿；
   - 实机 4 轮：一键领取（全选/单选各一轮）、活动作战（当期/往期各一轮）、周常挑战（两段各一轮）。
5. **用户可见变更**：`resource/announcement/Changelog.md` 写清"原 5 个领取任务并入「一键领取」，原 2 个活动任务并入「活动作战」…"，并标注 option 默认值。

**验收判据**：任务数 = 13；`verify` + `check_graph --strict` + `unittest` 三绿；4 轮实机无新增 `debug/on_error` 截图。

## 6. 落地记录（2026-10-21，部分执行：19 → 16 项）

本文档为完整方案；实际按用户指定只执行了 **2.1 领取类合并的拆分变体**，其余（活动类、周常类合并）暂不执行。

| 新任务 | 合并自 | 子链顺序（`[JumpBack]` 串接） |
|---|---|---|
| **一键领取** | 领取任务奖励 + 领取应对协议 | `DailyReward` → `CountermeasureProtocol` |
| **活动领取** | 领取邮件 + 活动-短期支援补贴 + 活动-每日行动补给 | `Mailbox` → `ShortTermCheckIn` → `DailyStaminaBonus` |

与 §2.1 原设计的差异：

1. **拆成两个入口而非合并为「一键领取」一项**：按用户要求把"任务/协议"与"活动/邮件"分开，任务列表 19 → 16（删 5 加 2）。
2. **未加「领取范围」多选 option**：原 5 项本就无 option，本次保持无 option 以免扩大改动面。若要支持"只领其中几项"，按 §2.1 的多选方案再加。
3. **顺序约束代替 option 粒度**：子链内部「活动未开放 / 应对协议已满级」的跳过分支是 `StopTask`（停整个任务），且**已实测无法改成"跳到下一环"**——这些出口位于导航链的 `[JumpBack]` 内层，改成空 next 会弹栈回导航父节点来回重扫（实测 `_DailyStaminaBonusNA` 自环 155 节点后超时）。MaaFW 没有跨调用层跳转机制，`StopTask` 是唯一能终止的出口。因此把可跳过子链**统一排在末位**，跳过时不留未执行项。若将来要实现"任意段跳过都不影响后续"，只能改成"每环独立入口 + MFA 任务队列"，而不是 pipeline 内部聚合。
4. **旧入口节点已删除**：`#CollectRewards` / `#CountermeasureProtocol` / `#Mailbox` / `#ShortTermCheckIn` / `#DailyStaminaBonus` 已无引用，会被 `check_graph --strict` 判为不可达，故一并移除（子链逻辑节点全部保留）。
5. **已实机验证（2026-10-21）**：14 项任务逐项冒烟 **13 OK / 1 FAIL**；`一键领取` 39.0s、`活动领取` 36.1s 均跑通。唯一失败的「当期活动」是内容过期（临界视域 2026-10-14 结束，主界面无 banner→`进入活动页` OCR 超时），非本次改动引入。另：**`[JumpBack]` 不能并列串子链**（会反复重跑第一条，实测 120s 内 `DailyReward` 循环 6 次），首版写法已证伪并改为硬链接。详细结果见 `docs/任务冒烟结果-2026-10-21.md`。

—— 详见 `开发记录.md` 2026-10-21 条目。
