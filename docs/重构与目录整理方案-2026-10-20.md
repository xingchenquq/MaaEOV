## 1. 现状诊断

### 1.1 根因：一个目录同时承担三种身份

MaaEOV 的根目录是**运行体、源码仓库、开发工作区**三者的并集：

```
根目录
├── 运行体      interface.json / resource/ / agent/ / config/ / exe+dll+runtimes+python
├── 源码仓库    agent/ resource/ scripts/ docs/ .github/ （与运行体高度重叠）
└── 开发工作区  debug/ logs/ temp/ backup/ dist/ .mfa_build/ .nicegui/ .mimosa/
```

这不是设计失误，而是 MaaFramework 的硬约束推导出的必然结果（见 §2）。但三者混居带来三个持续成本：

1. **新人/未来的自己无法判断"这个文件能不能删"** —— 需要读 `.gitignore` + `package_full.py` 的 `SKIP_DIRS` + `build_resource_zip.py` 的 `EXCLUDE_DIRS` 三处规则交叉推理，且三处规则互不一致。
2. **垃圾没有"到期"机制** —— `dist/` 攒到 424MB、`.mfa_build/` 195MB，每次发版新增 200MB 却无人清理，因为没有任何地方写"旧包可以删"。
3. **`.gitignore` 与实际的分类逻辑打架** —— 同样是"一次性脚本"，8 个入库、16 个被忽略（详见 §1.3-③）。

### 1.2 实测数据（2026-10-20）

工作目录合计约 **1.06 GB**，其中版本控制跟踪的部分只有约 **30 MB**：

| 分类 | 体积 | 说明 |
|---|---|---|
| 运行必需（不可移动） | ~310 MB | `python/` 142M、`MaaEOV.exe` 90M、`runtimes/` 59M、`libs/` 12.5M、`resource/` 26.6M 等 |
| 运行期产物（可清理） | ~622 MB | `dist/` 424M、`.mfa_build/` 194M、`debug/` 3.3M |
| 版本控制内部 | 51 MB | `.git` |
| 开发资产（跟踪） | ~0.4 MB | `agent/` `resource/` `scripts/` `docs/` `interface.json` 等 |
| **其中可直接回收** | **225 MB** | `dist/` 里的 v1.14.6 完整包（202M）+ 根目录重复的资源包（23.6M） |

### 1.3 五个具体症状

**① 根目录 10 个文件没有归属。**
`resource/base/image/` 有 14 个按功能域命名的子目录（`BCR/` `Homepage/` `SeaOfCognition/` `往期活动/` …），但同时有 10 张 PNG 直接躺在 `image/` 根：`公平交易.png`、`共时性.png`、`危机行动.png`、`危机行动调令.png`、`特别行动.png`、`巅峰时刻.png`、`火线特攻.png`、`虎胆龙威.png`、`铜墙铁壁.png`、`诡形物语.png`。
它们全部是 **BCR（基地）子系统**的小入口图，语义上属于 `BCR/`，却因为历史增量添加而留在根。后果：看目录的人不知道"哪些图是按域分的、哪些是散装的"。

**② 三份互不一致的排除规则。**

| 规则文件 | 排除了什么 | 与另两份的差异 |
|---|---|---|
| `.gitignore` | 二进制 / `python/` / `debug/` / `logs/` / `dist/` / `temp/` / `backup/` / `libs/` / `runtimes/` / `plugins/` / `.mfa_build/` / `.mimosa/` / `.workbuddy/` / `resource/mfa_layout.json` | 唯一考虑了"本机配置"的一份（`appsettings.json` 有意入库） |
| `package_full.py` 的 `SKIP_DIRS` | `.git` `.workbuddy` `temp` `debug` `docs` `scripts` `__pycache__` `.nicegui` `backup` `.mfa_build` `logs` `dist` | **未排除 `.github`、`.mimosa`** → 这两个会被打进发布包 |
| `build_resource_zip.py` 的 `EXCLUDE_DIRS` | 只在 `resource/` `agent/` 范围内排除：`raw/` `__pycache__` `debug` `logs` `temp` `backup` `.git` `.workbuddy` | 范围不同，正常；但 `resource/mfa_layout.json` 被排除，OTA 全量更新时用户自定义布局会被删 |

**③ "一次性脚本"被劈成两半。**
改动前 `scripts/` 有 24 个 py，`README.md` 明确标了其中 16 个为 `[一次性]`。但版本控制的实际状态是：

| 状态 | 数量 | 文件 |
|---|---|---|
| 入库 · 常备 | 3 py + 1 sh | `verify_feature` `gen_flow_doc` `pack_resource` `build_gui_mfa.sh` |
| 入库 · 一次性 | 8 py | `add_soc_focus` `apply_pipeline_split` `crop_soc_templates` `migrate_pipeline_v5` `recrop_ibb` `recrop_soc_buff_templates` `soc_trace` `split_pipeline` |
| **被 `.gitignore` 逐条忽略** | **13 py** | `check_roi` `check_versions` `crop_templates` `fix_soc_dive_flow` `fix_soc_entry_nav` `fix_soc_ocr_variants` `fix_soc_templates` `fix_template_paths` `grid_view` `loadres` `loadres2` `parse_mmor` `post_upgrade_tidy` |

（24 = 3 + 8 + 13；`README.md` 与 `build_gui_mfa.sh` 另计。）

于是"一次性脚本"这个分类在仓库里并不存在——它只是 README 里的一段文字，实际被切成了"入库"与"仅存于本机"两半，且切分依据从未说明。想看"历史上怎么修的"，得先知道哪一半在库里。

**④ 打包脚本不在仓库里。**
`.gitignore` 的 `/package_full.py`、`/build_resource_zip.py` 让**发版唯一通道**的脚本只存在于本机。换机、协作、或误删后，整套发布流程（含密钥消毒逻辑）需要从零重写。这两个脚本本身不含任何本机路径（`ROOT` 由 `__file__` 推导），入库没有安全风险。

**⑤ 197MB 的构建缓存没有明确归属。**
`.mfa_build/win-x64/` 是 MFAAvalonia 的构建产物（含 `MFAAvalonia.exe` + libs + runtimes + MaaAgentBinary）。它既不是源码也不是运行体，是"下次升级 GUI 时可能复用"的缓存。它已被 `.gitignore`（L63 `/.mfa_build/`）正确忽略，问题不在规则，而在**没有到期机制**：它与 `.nicegui/` `.mimosa/` 并列躺在根目录，三者性质相同（本机工具缓存）却没有任何地方说明"什么时候可以删"。

## 2. 硬约束：什么不能动

任何目录方案如果不尊重下面 6 条，执行完程序就起不来。这是本方案边界的前提。

| # | 约束 | 来源 | 后果 |
|---|---|---|---|
| 1 | `interface.json` 必须在程序根 | MFAAvalonia 按工作目录加载 | 移动即"找不到项目" |
| 2 | `resource/` 必须与 `interface.json` 同级 | `interface.json` 的 `resource` 字段为相对路径 | 图片/模型全丢 |
| 3 | `agent/` 必须在根（相对路径 `agent/main.py`） | `interface.json` 的 `agent` 块 | Agent 启动失败 |
| 4 | `config/` `debug/` `logs/` 由 MFA 宿主读写，位置固定 | 宿主硬编码 | 配置不生效 / 无日志 |
| 5 | 运行库（`python/` `runtimes/` `libs/` `plugins/` `Assets/` `*.dll` `SukiUI.xml`）必须与 exe 同目录 | .NET 程序集解析 + Python 嵌入 | 起不来 |
| 6 | CI 的 `paths` 触发器与 `run` 命令写死了 `scripts/` `docs/` 路径 | `.github/workflows/verify.yml` | 改了目录门禁失效 |

**结论：根目录的"可运行性"无法拆走。** 所有整理只能在"开发资产"和"运行期产物"两层做文章。

## 3. 目标目录结构

### 3.1 方案 A（推荐）：最小干预 + 分目录归位

不动 `scripts/` `docs/` 的位置（保持行业惯例与 CI 零改动），只做：垃圾清理、散图归位、一次性脚本归档、打包脚本入库。

```
MaaEOV/
├── interface.json              # ① 运行体（MFA 强制，不移动）
├── resource/
│   ├── base/
│   │   ├── pipeline/           # 20 个 json
│   │   ├── image/              # 14 个域目录，根目录 0 散图
│   │   └── model/ocr/          # det.onnx / rec.onnx / keys.txt（21MB，随资源包分发）
│   └── announcement/Changelog.md
├── agent/                      # 8 py + 新增 common/（§5 阶段 2）
├── config/                     # MFA 读写
├── python/ runtimes/ libs/ plugins/ Assets/   # 运行时
├── MaaEOV.exe  *.dll  SukiUI.xml  appsettings.json
├── debug/ logs/ temp/ backup/  # ② 运行产物（MFA 硬编码，不移动）
├── dist/                       # ③ 构建产物：只保留当前版本
├── .mfa_build/ .nicegui/ .mimosa/ .workbuddy/  # 本机工具缓存
│
├── scripts/                    # ④ 开发资产（位置不变）
│   ├── verify_feature.py       #    常备工具（CI 引用）
│   ├── gen_flow_doc.py
│   ├── migrate_layout.py       #    新增：本方案的执行工具
│   ├── package_full.py         #    建议入库（从根移入）
│   ├── build_resource_zip.py   #    建议入库（从根移入）
│   └── legacy/                 #    历史一次性脚本（新建）
├── docs/                       #    位置不变（CI 引用）
└── .github/ README.md LICENSE .gitignore 开发记录.md
```

**目录数从 20 项降到 17 项，0 散图，0 可回收垃圾，所有文件有明确归属。**

### 3.2 方案 B（可选演进）：把开发资产收敛进 `dev/`

```
MaaEOV/
├── dev/
│   ├── docs/          ← 从根 docs/ 迁入
│   ├── scripts/       ← 从根 scripts/ 迁入（含 legacy/）
│   └── build/         ← package_full.py / build_resource_zip.py
```

**收益**：根目录区分度最高——"带 exe 的是运行体，`dev/` 里全是给开发者看的"。
**成本**：需要同步改 7 处引用：

| 引用点 | 改动 |
|---|---|
| `.github/workflows/verify.yml` | `paths` 4 条 + `run` 2 条 |
| `package_full.py` | `os.path.join(ROOT,'scripts','verify_feature.py')` |
| `package_full.py` `SKIP_DIRS` | `scripts` `docs` → `dev` |
| `scripts/README.md` | 全部路径 |
| `docs/release.md` | 命令示例 |
| `docs/Agent启动失败排查.md` | 命令示例 |
| skill `maaeov-feature-add` / `maaeov-release` | 路径引用 |

### 3.3 选择建议

**一个人维护 → 选方案 A。** `dev/` 的收益是"根目录更整齐"，成本是 7 处引用 + 一个 skill 更新，且 CI 会红一次。收益不足以抵消。

**有协作者 / 准备开源贡献流程 → 选方案 B。** 此时"新人打开根目录能立刻分清哪些该看"的价值会上升，且一次性成本只付一次。

**两者都不做的底线**：至少完成 §4.1（清理 225MB）和 §4.3（散图归位）。这两项纯收益、零风险。

## 4. 文件处置清单

### 4.1 立即删除（可回收 225 MB）

| 路径 | 体积 | 理由 | 前置确认 |
|---|---|---|---|
| `dist/MaaEOV-v1.14.6-full-package.zip` | 202 MB | 已被 v1.14.7 取代；GitHub Release 上有存档，本地无需保留 | 确认 Release 页 v1.14.6 资产可下载 |
| `MaaEOV-resource.zip`（根） | 23.6 MB | 与 `dist/MaaEOV-v1.14.7-resource-win-x64.zip` 同源重复；根目录那个是旧命名残留（`pack_resource.py` 产物） | 对比两者文件清单一致 |

执行：`python scripts/migrate_layout.py purge --yes`

### 4.2 归档（新建 `scripts/legacy/`）

**入库的 8 个一次性脚本** → `scripts/legacy/`（用 `git mv` 保留历史）：

`add_soc_focus.py` `apply_pipeline_split.py` `crop_soc_templates.py` `migrate_pipeline_v5.py` `recrop_ibb.py` `recrop_soc_buff_templates.py` `soc_trace.py` `split_pipeline.py`

理由：它们在库里是为了"可追溯"，不是为了"可运行"。混在常备工具里会让每次 `ls scripts/` 都需要重新判断一遍哪个能跑。归档后 `scripts/` 根只剩 4 个常备脚本（`verify_feature` `gen_flow_doc` `pack_resource` `build_gui_mfa.sh`）+ 迁入的 2 个打包脚本 + 新增的 `migrate_layout.py`，一眼可辨。

**被 `.gitignore` 忽略的 13 个**（含本机绝对路径）→ **人工决定**，建议移到 `temp/legacy-scripts/` 或直接删除。不要在仓库里给它们建目录：它们本就不入库，建目录只会让"哪些在库里"更模糊。
> 本方案的脚本**不处理**这 13 个，只会在 `report` 里标为 `untracked`，避免误动。

执行：`python scripts/migrate_layout.py archive --apply`，然后手工改 `scripts/README.md` 的路径表。

### 4.3 归位（image 散图 → `BCR/`）

10 张图 → `resource/base/image/BCR/`，同步改写 22 处引用（`Shared.json` 21 处 + `CrisisMissionTickets.json` 1 处）。

| 图 | 语义 | 现引用 |
|---|---|---|
| `公平交易.png` `共时性.png` | 资源筹备内页 | `Shared.json` |
| `特别行动.png` `危机行动.png` `危机行动调令.png` | 特别行动/危机行动入口链 | `Shared.json` ×2、`CrisisMissionTickets.json` ×1 |
| `巅峰时刻.png` `火线特攻.png` `虎胆龙威.png` `铜墙铁壁.png` `诡形物语.png` | 资源筹备下的 5 个特训关 | `Shared.json` |

理由：它们全部属于 BCR 子系统，现有 `BCR/` 已有 27 张同域图。归位后 `image/` 根目录 0 散图，"按域分目录"的规则才真正成立。

**风险控制**：脚本做**文本级**替换（`"x.png"` → `"BCR/x.png"`），不 `json.load/dump`，因此 pipeline 里的 `//` 注释与缩进完全保留。替换后必须跑 `verify_feature.py` 确认模板存在性通过。

执行：`python scripts/migrate_layout.py images --apply && python scripts/verify_feature.py`

| 位置 | 问题 | 修法 |
|---|---|---|

## 5. 代码修改方案（分阶段）

每项给出：**目标 → 操作 → 产出 → 验收**。顺序按依赖排，不按重要性排。

### 阶段 0：基线锁定（0.5 天）

| 项 | 内容 |
|---|---|
| 目标 | 有任何改动前，先确认"现在是通过的状态"，并留下可比对的运行记录 |
| 操作 | ① `python scripts/verify_feature.py` 留存输出；② 跑一次完整日常（含喂一次危机行动调令 / 一次往期活动），保存 `debug/mfa_agent.log` 与 `logs/` 供后续对比；③ `git checkout -b refactor/layout` |
| 产出 | 基线日志 + 分支 |
| 验收 | 日志里能看到完整的节点序列（这也是验证 §5-6 日志落盘的前提） |

> 注意：当前 `debug/mfa_agent.log` 为 **0 字节**。基线跑完后如果仍是 0 字节，说明日志落盘链路本身有问题，`§5 阶段 1 第 6 项`（路径统一）应提前排查。

### 阶段 1：P0 缺陷修复（1 周）

这 8 项互不依赖，可并行；但都必须在阶段 2 之前完成（阶段 2 会移动这些代码）。

#### 1-1 抽出统一的点击封装

| | |

## 6. 执行顺序与门禁

```
        ┌─ 阶段 0 基线（0.5d）
        │
        ├─ 目录整理（0.5d，可与阶段 1 并行）
        │   purge → images → archive → 改 README/gitignore
        │
        ├─ 阶段 1 P0 八项（1w，可并行）
        │   1-1 点击封装（必须最先，阶段 2 会用到）
        │   1-2 ~ 1-6 agent 层局部修复
        │   1-7 ~ 1-8 校验修正
        │   ▼ 门禁：verify ALL_OK + 全 19 任务回归
        │
        ├─ 阶段 2 去重（1w）
        │   2-1 sweep 合并（依赖 1-1）
        │   2-2 删残留（依赖 1-7）
        │   2-3 Escape 一致性校验
        │   ▼ 门禁：verify ALL_OK + 危机行动/往期活动各跑一次
        │
        ├─ 阶段 3 Shared 拆分（1–2w）
        │   ▼ 门禁：verify ALL_OK + 全 19 任务回归
        │
        ├─ 阶段 4 性能（2–4w，逐项 A/B）
        │   ▼ 门禁：每项单独对比耗时，无新增失败才保留
        │
        └─ 阶段 5 工程化（持续）
```

**三道硬门禁，缺一不可**：

1. `python scripts/verify_feature.py` → `RESULT: ALL_OK`
2. 受影响任务实机跑通（不是"看起来对"，是跑完）
3. `git diff` 里没有意外文件（尤其别把 `debug/` `config/config.json` 带进去）

**阶段 1 结束时的专项验收**：跑一次完整日常，对比 `debug/mfa_agent.log` 与基线日志，确认「点击失败」「OCR 失败」「超时」三类事件都能在日志里看到**根因级**信息，而不只是最终那条 `Task timeout`。这是本轮重构唯一的硬指标。

## 7. 风险与回滚

| 风险 | 触发条件 | 缓解 | 回滚 |
|---|---|---|---|
| 图片归位后识别失败 | 路径改写不完整 | 文本级替换 + `verify` 模板存在性检查 | `git checkout resource/` + `git checkout interface.json` |
| `click` 重试引入延迟 | 坐标本身错误时每点重试 3 次 | 重试上限 2 次、间隔 0.2s；坐标错误属配置问题，重试只增加 ~0.4s | 把 `retries` 设 0 |
| 1-3 改 `return False` 导致任务失败 | 存在"战斗已结束但界面未刷新"的合法场景 | 参数化 `fail_on_timeout`，默认 True 但可单节点覆盖 | pipeline 里配 `fail_on_timeout=false` |
| Shared 拆分引入同名冲突 | 跨文件重复定义 | `verify` 第 4 段是硬失败，天然阻断 | 单文件回滚 |
| 归档 `scripts/legacy` 后 CI 找不到脚本 | `verify.yml` 引用了被移动的文件 | 移动前先 grep 引用（脚本会提示） | `git mv` 反向 |
| 阶段 4 等待分级导致识别抖动 | 画面未稳定就开始识别 | 灰度一个任务先验；保留原值到对比通过 | 恢复 `post_wait_freezes` |

## 8. 配套工具用法

```bash
# 1) 只读盘点（默认，永不修改任何文件）
python scripts/migrate_layout.py

# 2) 图片归位（先看 dry-run，再执行）
python scripts/migrate_layout.py images
python scripts/migrate_layout.py images --apply
python scripts/verify_feature.py        # 必须 ALL_OK

# 3) 一次性脚本归档（仅处理已 git 跟踪的 8 个）
python scripts/migrate_layout.py archive --apply

# 4) 清理过期产物（白名单，225MB）
python scripts/migrate_layout.py purge            # 只看清单
python scripts/migrate_layout.py purge --yes      # 实际删除
```

**工具边界**（有意为之，不做"聪明"的事）：

- 不移动 `interface.json` / `resource/` / `agent/` / `config/` —— MFA 硬约束
- 不处理未被 git 跟踪的本机专用脚本 —— 它们含本机绝对路径，处置需人工确认
- 不递归删除任何目录 —— `purge` 只删白名单里的**文件**
- 不改 JSON 结构 —— `images` 只做字符串替换，保留 pipeline 注释
