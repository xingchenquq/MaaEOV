## 步 0：通知能力实测核验（30 分钟）

### 目标

把三个"从源码推断"的事实变成"实测确认"，避免基于错误假设写文档。

需要确认的三件事：

| # | 问题 | 推断答案 | 为什么必须实测 |
|---|---|---|---|
| Q1 | 外部通知页有几个渠道卡片？ | 12 个（无 QQ 机器人） | 本地 MFA 源码是 Maadori 定制分支（13 个），MaaEOV 用的是上游 v2.16.1 基线（`MaaEOV.exe` 构建于 2026-09-13，定制提交 2026-10-23 才归档） |
| Q2 | **任务失败时会不会发通知？** | 会（`MaaProcessor.cs:4524`） | GUI 界面自己的提示文案写着"仅会发送'所有任务完成'的通知"，**与代码矛盾**，必须实测定论 |
| Q3 | 用 `StopTask` 收尾的"跳过"任务，算完成还是算失败？ | 算"已停止"，**不通知、也不执行结束后操作** | 决定"跳过要不要告警"的口径 |

### 前置条件

- MaaEOV 能正常启动（不需要游戏在跑）
- 一个能收 HTTP 请求的临时地址（**零账号，30 秒拿到**）

### 操作步骤

**0.1 拿一个回调地址**

浏览器打开 <https://webhook.site>，页面右侧会给你一个唯一 URL，形如
`https://webhook.site/1a2b3c4d-....`。**这个页面保持打开**，收到的请求会实时显示。

> 用 `webhook.site` 而不是 Server酱/Telegram，是因为它零注册、不用梯子、能直接看到请求体内容。验证完就关掉，不产生任何账号残留。

**0.2 配渠道**

MaaEOV → 设置（左侧齿轮）→ **外部通知** → 找到 **通用 Webhook**（`CustomWebhook`）卡片：
- Webhook URL 填 0.1 拿到的地址
- 勾选"启用的通知配置"里的该渠道
- 点 **发送测试**

✅ 判据 A：webhook.site 页面出现一条请求，body 里含测试文案 → 渠道链路通。
❌ 若没反应：先看 `logs/log-YYYYMMDD.log` 里 `[WRN]/[ERR]` 行，再继续。

**0.3 验 Q2：失败会不会通知**

保持游戏**不启动**（模拟器关掉），回到主界面勾选任务 **启动游戏**，点开始。它必然失败。

✅ 判据 B1：webhook.site 出现**第二条**请求，内容含"任务失败"或你自定义的失败文案 → **失败会通知**，界面那句 Tips 是过时文案。
✅ 判据 B2：只有一条（步 0.2 的测试）→ **失败不通知**，差距比分析报告写的更大，步 4 优先级要上调。

**0.4 验 Q3：跳过算哪种状态**

启动游戏，等它进到主界面。勾选 **危机行动调令**（若当前调令为 0），运行。

✅ 判据 C：界面日志显示"已停止"而非"已完成" → 确认 `StopTask` 走 STOPPED 分支
✅ 同时观察：webhook.site **没有**新请求 → 确认"跳过不告警"
✅ 若你之前设了"结束后操作=关机"，这一步**不会关机** → 记录这个坑（无人值守闭环的隐性断点）

**0.5 记录**

把结论写进 `docs/对标MAA-通知与GUI-2026-10-23.md` 的 §1.1 版本校准表下方，格式：

```markdown
### 实测结论（2026-10-23 实机）
- 渠道卡片：__ 个（有/无 QQ 机器人）
- 失败通知：会 / 不会
- STOPPED 任务：Notified=否，AfterTask 执行=否
- 测试渠道：CustomWebhook → webhook.site，收到 __ 条
```

### 产出

三行实测结论 + 一份"渠道可用性"判断。

### 分支决策

| 实测结果 | 后续动作 |
|---|---|
| B1（失败会通知） | 按原计划走步 1-3，步 4 不急 |
| B2（失败不通知） | 步 1 文档里**不能**承诺"失败会推送"；步 4 提为 P1，考虑先打一个最小 GUI 补丁（把 4524 行的调用补上 if 分支） |

## 步 2：跳过与中止的 GUI 可见性（0.5 天）★ 性价比最高

### 目标

让用户在界面日志里**看到为什么什么都没做**，而不是只看到"任务完成"。

### 现状（已实测）

| 事实 | 证据 |
|---|---|
| 21 个 pipeline 文件里共 **4 个 `StopTask` 节点**，**全部没有 `focus`** | 脚本枚举结果见下 |
| 全部 `focus` 文案里，**没有一条**说明"跳过 / 不足 / 未适配" | `grep focus` 全文无匹配 |
| 4 个节点 | `DailyStaminaBonus.json: _DailyStaminaBonusNAFromEvent`、`JointBlockade.json: JointBlockadeUnfinishedGame`、`Shared.json: _HaltTask`、`ShortTermCheckIn.json: _ShortTermCheckInNAFromEvent` |

用户视角：清体力因体力不足提前停 → 界面显示"任务完成" → 用户以为刷完了，实际一点没刷。

### 前置

无。与 P0-2 的 timeout 改造**不冲突**（不碰 timeout 行）。

### 操作步骤

**2.1 先穷举全部"提前结束"出口**

不要只改已知的 4 个。跑这个脚本，把所有"跳过"语义的出口列全：

```bash
cd /c/Users/Lee/Documents/Python/MaaEOV
python - <<'EOF'
import re, json, glob, os
def load(p):
    s = open(p, encoding='utf-8').read()
    s = re.sub(r'^\s*//.*$', '', s, flags=re.M)
    s = re.sub(r'/\*.*?\*/', '', s, flags=re.S)
    s = re.sub(r',(\s*[}\]])', r'\1', s)
    return json.loads(s)

KEY = ('NA', 'Skipped', 'Halt', 'Unfinished', '为零', '结束', 'Insufficient')
for p in sorted(glob.glob('resource/base/pipeline/*.json')):
    d = load(p)
    for name, node in d.items():
        if not isinstance(node, dict):
            continue
        act = node.get('action')
        a = act if isinstance(act, str) else (act or {}).get('type')
        is_stop = (a == 'StopTask')
        is_terminal = (node.get('next') == [])
        if (is_stop or (is_terminal and any(k in name for k in KEY))):
            print('%-34s %-40s stop=%-5s focus=%s' % (
                os.path.basename(p), name, is_stop, 'focus' in node))
EOF
```

把输出里 `focus=False` 的行作为改造清单。

**2.2 给每个出口补 focus**

在节点里加一行（`focus` 与 `action` 同级）：

```json
"_HaltTask": {
    "focus": {
        "Node.PipelineNode.Starting": "已中止：条件不满足（详情见 debug/mfa_agent.log）"
    },
    "action": "StopTask",
    ...
}
```

文案规范：**"做了什么 + 为什么"**，不超过 20 字，别写节点名。

参考写法：

| 节点 | focus 文案 |
|---|---|
| `_HaltTask` | 已中止：条件不满足，本次跳过 |
| `_DailyStaminaBonusNAFromEvent` | 每日行动补给：活动未开放，已跳过 |
| `_ShortTermCheckInNAFromEvent` | 短期支援补贴：活动未开放，已跳过 |
| `JointBlockadeUnfinishedGame` | 联线封锁：存在未完成对局，已跳过 |
| `CrisisMissionTicketsSkipped` | 危机行动：调令已为 0，已跳过 |

> 注意：`focus` 的 key 必须是 `Node.PipelineNode.Starting`（渲染时机），不要用 `Completed` —— 跳过节点不会走 Completed。

**2.3 校验**

```bash
python/python.exe scripts/verify_feature.py     # 期望 RESULT: ALL_OK
python/python.exe scripts/run_tasks.py --task 危机行动调令   # 实机跑一次跳过路径
```

### 产出

6~10 处 `focus` 增加，一个更精确的"跳过出口清单"（可入库到 `docs/`）。

### 验收判据

构造一个跳过场景（调令为 0 / 体力不足），界面运行日志必须出现你写的那句中文，且**不是**"任务完成"。

### 风险

低。`focus` 是纯展示字段，不影响执行逻辑。唯一注意：同一任务里 focus 文案别重复到分不清哪一步。

## 步 3：`debug/events.jsonl` 事件文件（0.5 天）

### 目标

把 agent 已有的结构化事件（`result: ok/fail/skip`）落到一个**稳定格式的单一文件**，为将来的通知/UI 消费备好数据源。**这一步不发通知**，只建管道。

### 现状

| 已有 | 位置 | 问题 |
|---|---|---|
| `mfalog` 结构化日志 | `debug/mfa_agent.log`（行为 `[MFA]{json}`，含 `seq`/`task_id`/`result`） | 混着所有级别的日志，消费方要自己过滤 |
| `task_trace` | 同上 | 无独立事件流 |
| `evidence` / `diagnostics` | `debug/evidence/*.png+json` | 每对文件独立，无索引 |
| stdout | **被 GUI 丢弃** | 不可达 |

### 前置

无。与步 2 可并行。

### 操作步骤

**3.1 定义 schema（先定死，别边写边改）**

`debug/events.jsonl`，每行一个 JSON：

```json
{"ts":"2026-10-23T15:40:12.345+08:00","task":"清体力","entry":"#Farm","node":"FarmDone","result":"skip","reason":"体力不足","evidence":"debug/evidence/FarmDone_20261023_154012.png","elapsed_s":42.1}
```

字段约束：
- `result` 只允许 `ok` / `fail` / `skip`（与 `mfalog` 词表一致）
- `task` 用 `interface.json` 里的中文任务名（用户能看懂）
- `evidence` 可空
- 单行、UTF-8、追加写、`flush`

**3.2 在 `task_trace` 里加写入口**

`agent/task_trace.py` 已有任务开始/结束的事件回调，在任务终止处（正常 / 中止 / 异常三条路径）各写一行。**复用 `evidence.py` 的 TTL 与上限逻辑**（`MAX_AGE_S=24h`、`MAX_PAIRS=200`），避免文件无限增长 —— 建议上限 500 行，超了轮转成 `events.jsonl.1`。

**3.3 与 `mfalog` 解耦**

不要改 `mfalog._emit`（它已经被 stdlib logging 共用，动它风险大）。新增一个 `agent/events.py`，由 `task_trace` 调用。`mfalog` 与 `events` 各写各的。

**3.4 校验**

```bash
python/python.exe scripts/run_tasks.py --task 一键领取
wc -l debug/events.jsonl          # 与运行的任务数一致
python/python.exe -c "import json;[json.loads(l) for l in open('debug/events.jsonl',encoding='utf-8')]"  # 每行合法
```

### 产出

- `agent/events.py`（新建，~60 行）
- `agent/task_trace.py`（+3 处调用）
- `debug/events.jsonl`（运行期产物，需加进 `.gitignore`）

### 验收判据

跑 3 个任务（1 成功 / 1 跳过 / 1 故意失败），`events.jsonl` 恰好 3 行，`result` 分别为 `ok` / `skip` / `fail`。

### 风险

中低。注意两点：
- **写文件失败不能影响任务**（`try/except` 吞掉，与 `mfalog._emit` 的处理方式一致）
- `agent/` 改动**必须随完整包发版**，资源 OTA 包不含 `agent/`

## 步 4：是否维护 MFA fork（决策，1 天评估）

### 目标

给出 go / no-go，不做实施。

### 前置

步 0 的实测结论（尤其 Q2）+ 步 3 的 `events.jsonl` 跑通。

### 决策依据（三项，缺一不可）

| 指标 | 怎么量 | go 的门槛 |
|---|---|---|
| 需求真实存在 | 发版公告 + 文档上线后，看有多少用户反馈"配了通知" / 问"为什么没收到" | ≥ 5 人明确使用 |
| 缺口确认 | 步 0 的 Q2 若为"失败不通知"，缺口成立 | 缺口成立 |
| 维护成本可控 | MFA 上游版本节奏（v2.16.1 → 下一版间隔）、我们的补丁行数 | 补丁 ≤ 200 行，且与上游重叠文件 ≤ 3 个 |

### 若 go：只做两个补丁

| 补丁 | 落点 | 工作量 |
|---|---|---|
| **内容匹配通知** | GUI 新增读取 `debug/events.jsonl` 的定时器，按 `result != ok` 推送 | 1.5 人日 |
| **卡死检测** | 监听 `Tasker` 节点事件，连续 N 分钟无事件 → 推"疑似卡住" | 1 人日 |

**明确不做**（已论证）：`SendAfterLogCount`（进度播报）、`SendBeforeScheduledStart`（定时预告）、多渠道路由、远程控制 API、Copilot、工具箱、运行时长上限、前后置脚本。

### 若 no-go：收口

把步 3 的 `events.jsonl` 降级为"仅诊断用"，文档里不承诺任何通知能力，只保留步 1 + 步 2 的成果。

## 附 A：不要做的事（已论证，避免返工）

| 想法 | 为什么不做 |
|---|---|
| 给 13 个 `Yes/No` option 加 `type:"switch"` | **已经自动渲染成开关了**。`TaskOptionGenerator.cs:194` + `ShouldSwitchButton`（case 数==2 且含 yes/no）已覆盖，加了也是白加 |
| 补给站 5 个开关合成 checkbox 组 | 要重构 5 组 `enabled:true/false` 双分支 override，收益只是 UI 少 4 行 |
| 清体力 34 项改 `case.option` 级联 | ComboBox 已带搜索（`SetCanSearch(true)`），搜索覆盖 80% 场景；级联要重构 override 结构 |

| 把 `StopTask` 改成判失败以触发通知 | 会让失败率统计失去意义。"体力不足"是正常结束，不是故障 |
| 一次性抄 MAA 的全套 Delivery 策略 | 14 个字段里只有 2 个对我们有真实价值（内容匹配、卡死检测），其余无场景 |
