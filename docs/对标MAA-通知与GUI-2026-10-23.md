# 对标 MAA：通知渠道、GUI 与任务设计

> 对标对象：MAA v6.20.1 发布包（`C:\Users\Lee\Documents\Python\MAA`，含 `config/gui.new.json` 全量配置）
> 自身基线：MaaEOV v1.15.0 + MFAAvalonia v2.16.1
> 方法：读配置 + 读 GUI 源码（`MFAAvalonia/`）+ 读本地 pipeline/agent。**所有结论均有一手证据，不靠印象。**
> 日期：2026-10-23

## 0. 结论先行

| 维度 | 判断 | 一句话 |
|---|---|---|
| 通知渠道 | **真差距** | MFA 给了 12 个渠道（与 MAA 的 12 个基本对齐），但 MAA 的价值在"什么时候发、发什么、带什么上下文"的**策略层**，我们这层是空的，且当前**一个渠道都没配**。 |
| GUI | **不是差距，是没暴露** | MFA 2.16.1 与 MAA GUI 同血统，定时/托盘/完成后关机/多配置/新手引导/主题/日志导出全都在。用户不知道这些存在。 |
| 任务设计 | **模型一致，我们更彻底** | 16 任务 / 21 组 option / 101 个 case；`Yes/No` 已自动渲染成开关（代码实测，见 §2.4）。合并粒度方向正确。真差距只有一条：**失败后用户看不到任何证据**。 |

**最重要的单点结论**：我们最值钱的三套工程设施（结构化日志 `mfalog`、任务追踪 `task_trace`、失败取证 `evidence`/`diagnostics`）**出口只有磁盘文件**。用户看不到、GUI 看不到、通知也接不上。这不是"缺功能"，是"建好了没接线"。

## 1. 通知渠道

### 1.1 MAA 的四层结构

MAA 把通知拆成四层，每层独立演进。看清这个分层，就知道我们缺的是哪一层。

| 层 | 职责 | MAA 的实体 | 我们的对应物 |
|---|---|---|---|
| **L1 事件源** | 何时触发 | 完成 / 失败 / **卡死(25min)** / **定时前(5min)** / **每 N 条日志** / **日志内容正则** | 完成 / 失败（2 个，`MaaProcessor.cs:4524/4574`）；无"开始"事件 |

> ⚠️ **版本校准（2026-10-23 补）**：本报告初稿把触发点写成"完成/失败/开始 3 个"，那是**本地 `MFAAvalonia` 仓库（Maadori 定制分支，`v2.16.1-3-gf4934df`）** 的行为。MaaEOV 打包的是**上游 v2.16.1 基线**（`MaaEOV.exe` 构建于 2026-09-13，定制提交 2026-10-23 才归档）。以 `git show v2.16.1:` 为准的差异如下：
>
> | | 上游 v2.16.1（= MaaEOV 实际） | Maadori 定制分支 |
> |---|---|---|
> | 渠道数 | **12**（无 QQ 机器人） | 13（+QQBot） |
> | 通知触发点 | **完成、失败**（2 个） | 完成、失败、开始（3 个） |
> | 附图 + 最近日志 | **无** | 有 |
> | 自定义通知文案 | 有（`EnabledCustom` / `CustomSuccessText` / `CustomFailureText`） | 同 |
>
> 另注：上游 GUI 的说明文案 `ExternalNotificationTips` 写的是"**仅会发送'所有任务完成'的通知**"，与代码不符（失败也会发）——**别信界面这句提示**。

| **L2 投递策略** | 发不发、带什么 | `Gui.ExternalNotification.Delivery`（14 字段） | **无** |
| **L3 渠道适配** | 怎么发 | `Configs: []` 多组并存，每组独立凭据 | 12 渠道，`ExternalNotificationEnabled` 逗号列表 → **全渠道广播** |
| **L4 内容组装** | 长什么样 | 标题 + 正文 + **历史日志上下文** | 固定模板（成功/失败两套文案） |

**判断：L3 我们赢（渠道比 MAA 多），L1 打平，L2 和 L4 是空的。**

### 1.2 L2 才是 MAA 的核心设计

MAA `Delivery` 的 14 个字段（`config/gui.new.json:306-324`），拆开看是四组正交能力：

| 字段 | 语义 | 我们的状态 | 值不值 |
|---|---|---|---|
| `SendWhenComplete` | 正常完成时发 | 有（写死） | — |
| `SendWhenError` | 失败时发 | 有（写死） | — |
| **`SendWhenStalled`** + `Notification.EnableStallTimeout` / `StallTimeoutMinutes: 25` | **卡住 N 分钟无进展 → 发** | **完全没有** | **高** |
| **`SendWhenContentMatches`** + `Whitelist` / `Blacklist` | **日志命中正则 → 发** | **完全没有** | **最高** |
| `SendAfterLogCount` + `NewLogCount: 10` | 每 N 条日志推一次（进度播报） | 没有 | 中 |
| `SendBeforeScheduledStart` + `ScheduledStartNotificationMinutes: 5` | 定时启动前预告 | 没有 | 低 |
| `IncludePreviousLogs` / `MaxEntries: 100` / `TimeMinutes: 60` / `FilterPreviousLogs` | 附带最近日志上下文 | 没有 | 中 |

**为什么 `SendWhenContentMatches` 对我们价值最高**：它是一条"日志 → 通知"的通用管道。我们已经在 `agent/mfalog.py` 里把每条业务事件打成 `[MFA]{json}`、带 `result: ok/fail/skip`。**只差一个消费者**。有了它，"体力不足已停止""往期活动未适配已跳过""调令数=0"这类我们当前只能写进文件的事件，立刻可以变成用户手机上的一条推送。

### 1.3 L3 的差异：MAA 并存，我们广播

| | MAA | MFA / 我们 |
|---|---|---|
| 配置模型 | `Configs: []` 数组，每组独立（企业微信机器人 + 邮件 + Server酱可同时各配一份） | 单一 `ExternalNotificationEnabled` 逗号列表 |
| 发送行为 | 每组按 `Delivery` 策略独立判断 | 遍历启用列表 **全发**，同一文案、同一时机 |
| 事件路由 | 天然支持（不同 Config 不同策略） | 只能靠改代码加 `qqBotOnly` 这类参数（Maadori 定制分支就是这么干的） |

实际影响不大：MaaEOV 用户只有一个账号，不需要"工作微信和工作邮箱分流"。**不建议补这一层。**

### 1.4 结构性障碍：agent 的事件到不了 GUI，也到不了通知

这是本次分析最重要的发现，有四处一手证据：

| 证据 | 内容 |
|---|---|
| `agent/mfalog.py:84-86` | 注释明写："Agent 子进程的 stdout 会被 MFA GUI 丢弃（不进 GUI 日志、也不进 maafw.log）"，因此才同步落盘到 `debug/mfa_agent.log` |
| `agent/diagnostics.py:66` | 中止留痕只调 `mfa_log(...)`，无任何 GUI 写入 |
| `agent/evidence.py` | 失败取证（ROI 图 + OCR 命中值 + 模板得分 + 阈值）全部写 `debug/evidence/`，24h TTL |
| `agent/task_trace.py` | 任务开始/摘要只进 `debug/mfa_agent.log` |

**结论：我们做了全套"可观测性"，但观测对象只有开发者自己。** 终端用户跑失败后，界面上看到的还是一句"任务失败"，想弄清原因必须有人告诉他去翻 `debug/`。

对照 MAA：失败卡片直接内联最近日志，`IncludePreviousLogs` 把上下文一起推到手机。**它把"排查"当成产品功能，我们把"排查"当成开发工具。**

### 1.5 改进建议（按成本分三档）

#### N0 — 零代码，本周可做

| # | 动作 | 具体 |
|---|---|---|
| N0-1 | 写"无人值守配方" | README 加一节：设置 → 外部通知（填 Telegram/Bark/Server酱任一）→ 定时（8 档）→ 结束后操作（关机/关闭模拟器）。**这三件套 MFA 全都有，用户 90% 不知道。** |
| N0-2 | 发版公告带一句 | Changelog「改进」加一条指向配方文档 |
| N0-3 | 明确告警口径 | 现在 `StopTask` 收尾的任务在 GUI 判为"已停止"（STOPPED 分支），**既不通知也不触发结束后操作**。这类"可预期跳过"要不要通知，得先定口径：**默认不发**，因为"体力不足"是正常结束，不是故障。 |

> N0-3 是必须先定的口径。MaaEOV 大量用 `StopTask` 做跳过出口（跳过 → 判成功），这与"跳过要通知"天然冲突。**别为了通知去把跳过改成失败**——那会让失败率统计失去意义。

#### N1 — 改 agent + 资源，不动 GUI（推荐先做这个）

| # | 动作 | 做法 | 成本 |
|---|---|---|---|
| N1-1 | 建事件文件 | `task_trace` 在任务结束/中止时，追加一行到 `debug/events.jsonl`：`{ts, task, entry, result, reason, evidence_path}` | 0.5 人日 |
| N1-2 | 保留期与上限 | 复用 `evidence.py` 的 TTL/上限逻辑，避免无限增长 | 同上 |
| N1-3 | 失败时把路径"喊"到 GUI | MFA 失败 Toast 文案可用 `LangKeys` 定制 → 在失败提示后追加固定指引"取证见 debug/evidence/"。**只能固定文案**（agent 动态内容进不了 GUI，这是硬约束） | 0.5 人日 |

N1 的产出不是"能发通知"，而是**把通知所需的数据源准备好**。真正发通知要 N2。

#### N2 — 动 GUI 分支（只在确定要长期维护 MFA 分支时做）

只抄两个字段，别全抄：

| # | 动作 | 理由 | 成本 |
|---|---|---|---|
| N2-1 | **`SendWhenContentMatches`**：GUI 侧 tail `debug/events.jsonl`，按 `result: fail` 或白名单正则推送 | 唯一能把 agent 业务事件变成通知的通道；直接复活我们的 `mfalog` | 1.5 人日 |
| N2-2 | **卡死检测**：连续 N 分钟无 `Tasker` 节点事件 → 推"疑似卡住" | 我们有 8~10 分钟级的战斗与推图链；用户白天挂着上班，卡住 3 小时才发现是真实痛点 | 1 人日 |
| N2-3 | 附带最近日志上下文（`MaxEntries` / `TimeMinutes`） | 让手机上的通知本身可定位，不用回电脑翻文件 | 0.5 人日 |

**明确不做**：`SendAfterLogCount`（进度播报，日常脚本一次性跑完，收益低）、`SendBeforeScheduledStart`（预告，场景不存在）、多渠道并存路由（单账号无需求）、`RemoteControl`（远程控制，无此场景）、第三方上报（企鹅物流/一图流，无对应生态）。

> ⚠️ **N2 的前置**：我们的 `agent/` 不能进资源 OTA 包（这是既有发版约束）。N2-1 若依赖 agent 写的新事件文件，**必须随完整包发**，否则用户更新资源包后 GUI 读一个永远不存在的文件。

## 2. GUI 与任务设计

### 2.1 MAA 的设计要点（七条）

1. **信息架构三栏**：左任务队列（拖拽排序、开关、右键）／中参数区／右日志+实时画面。MFA 同构。
2. **参数控件按语义定制**：关卡选择器带关卡名 + 掉落物 + 理智效率；干员选择器带练度。**不是给一串字符串。**
3. **任务状态独立可见**：每个任务有自己的"未开始/运行中/完成/失败/跳过"，失败卡片内联日志片段。
4. **无人值守闭环**：8 档定时（可绑不同配置）＋ 结束后动作（关机/休眠/退出）＋ 托盘 ＋ 全局快捷键 ＋ 阻止睡眠 ＋ **运行时长上限**。
5. **可恢复的工作现场**：多套配置（Configuration）一键切换、窗口位置记忆、设置项可排序、折叠状态记忆。
6. **自助排查**：一键导出日志、失败截图、内置 Changelog/公告、问题反馈入口。
7. **生态延伸**：Copilot 抄作业、工具箱（仓库识别/干员 box/抽卡记录）。

**读法**：标 ⚠️ 的六项，**MFA 全部支持、用户全部可配、我们一句没讲**。这是本次分析里 ROI 最高的地方——不改一行代码，只改文档，感知提升最大。

### 2.3 真正的差距只有三条

1. **无人值守三件套没暴露**：定时 + 结束后动作 + 外部通知，能力齐备、零引导。用户以为 MaaEOV 只能"坐在电脑前点一下"。
2. **失败后的自查入口为零**：`evidence`/`diagnostics`/`task_trace` 全落文件，GUI 零可见（§1.4）。这是唯一需要动工程的差距。
3. **长下拉无级联**：`清体力-选择关卡` 34 项、`危机行动调令-选择关卡` 18 项，全靠一个下拉。MFA 的 ComboBox 带搜索（`SetCanSearch(true)`，`TaskOptionGenerator.cs:763`），可用性尚可；MFA 还支持 `case.option` 级联（选了父项才展开子项）与 case 级 `icon`，我们都没用。**优先级低**——搜索已覆盖 80% 场景，级联要重构 override 结构，不值。

### 2.4 任务设计对照

**模型其实一致**：

| | MAA | MaaEOV |
|---|---|---|
| 任务定义 | 强类型 C# 模型（`FightTask` / `AwardTask` / `RoguelikeTask`...） | `interface.json` 的 `task[]`：`entry` + `option[]` |
| 任务内参数 | 模型字段直接绑 UI | `option` → `cases` → `pipeline_override` |
| 任务开关 | `IsEnable` | 队列勾选 |
| 参数持久化 | 每任务字段落 `gui.json` | MFA 落 `config/instances/*.json` |

MAA 一个 `FightTask` 有 ~25 个字段、`RoguelikeTask` ~60 个；我们 16 个任务共 21 组 option / 101 个 case，平均每任务 1.3 组。**差距不在"参数多少"，在"参数是怎么来的"**：MAA 的参数是开发者手写强类型 + 定制控件；我们的参数是 JSON 声明 + MFA 自动生成控件。

**一个必须纠正的直觉**（本次实测）：`MFA` 的 `TaskOptionGenerator.cs:194-195` 是这么选控件的——

```csharp
else if ((interfaceOption.IsSwitch && interfaceOption.Cases.ShouldSwitchButton(...)) ||
         interfaceOption.Cases.ShouldSwitchButton(...))   // 没有 type 也会自动判
```

而 `ShouldSwitchButton`（`MFAExtensions.cs:400-430`）的判定是：**case 数 == 2 且 名字含 `yes`/`no`（不区分大小写）**。

所以：**我们那 13 组 `Yes`/`No` 的 option 现在就已经渲染成开关了，不需要加 `type: "switch"`。** 之前的"参数表达力被浪费"猜想不成立。真正没用到的是 `checkbox`（多选组）和 `input`（数值）。

候选改造只有一处值得做：

| 现状 | 候选 | 判断 |
|---|---|---|
| `补给站` 5 个独立 `Yes/No` 开关（领货柜 / 银锡数据 / 外部招聘书 / 急务招聘书 / 紫锡数据） | 合成 1 个 `checkbox` 组 | **可以，但不划算**。转 checkbox 要求把每组的 `enabled:true/false` 双分支改成"选中即 true"单分支，要重构 5 组 override；收益只是 UI 少 4 行。**收益 < 成本，不做。** |

**任务粒度：我们比 MAA 更彻底，这是优点不是缺点。**

MAA 的 `AwardTask` 用 8 个子开关（`Award`/`Mail`/`FreeGacha`/`Orundum`/`Mining`/`SpecialAccess`/`SignInEvent`），因为明日方舟的"免费单抽""基建挖矿"有玩家主观分歧。MaaEOV 的"一键领取""活动领取"是**硬链接合并**（`Aggregated.json`：`DailyReward → CollectWeeklyReward → CountermeasureProtocol`），没有子开关。

**这不是退步。** 异象回声的领取项全是纯收益、无分歧，多给 3 个开关只会增加决策负担。MAA 那 8 个开关是**被迫**的，不是先进。**别抄。**

## 3. 排期建议

| 序 | 编号 | 内容 | 依赖 | 备注 |
